## 二、M1 建成了什么

### 2.1 三层结构，引擎源码零改动

```
Electron 主进程 (app/electron/)          ← 配置、密钥、进程守护、事件回流
        │  spawn（stdio 走文件，不走管道）
        ▼
启动器 runner/engine-launcher.mjs        ← 把界面配置翻译成引擎能吃的 SETTINGS_JSON + profile
        │  node main.js（vendor 引擎，一行没改）
        ▼
MindServer ──spawn──▶ agent 子进程        ← 我们注入的"聊天门"在这里生效
```

- **唤醒全靠门，不靠引擎**：引擎本身**没有**"称谓"概念（`docs/03` §九），公屏上任何人的任何一句话都会触发一次大模型调用。
  门用 `Agent.prototype._setupEventHandlers` 包装，在引擎注册完监听器后**精确摘掉新增的那两条**
  （实测 `removedEngineListeners=2`），换挂我们自己的 `chat`/`whisper` 监听器。
- **绝不动 `vendor/` 里的业务代码**。唯一改过引擎的文件是新增的 `src/models/mcbot.js`（一个自研的 OpenAI 兼容适配器）
  ——它是**新增**文件，不是修改上游文件。

### 2.2 关键文件清单

| 位置 | 作用 |
|---|---|
| `app/electron/supervisor.mjs` | 生命周期：起停、退避重连、状态机、`taskkill /pid /T /F` 按 PID 树杀（**绝不按镜像名杀**） |
| `app/electron/launcher.mjs` | 把 `AppConfig` 的 bot/server/llm 翻译成 launch spec；**API Key 只走环境变量，不落盘** |
| `app/electron/store.mjs` | 配置读写 + `safeStorage` 密钥托管（不可用时降级明文并**明确告知用户**） |
| `app/electron/events.mjs` | 500ms 轮询 tail 各 bot 的 jsonl（**不用 `fs.watch`**，Windows 上对追加写语义不稳） |
| `app/electron/ipc.mjs` | 21 个 IPC channel；事件翻译成界面契约 |
| `app/electron/llm.mjs` | OpenAI 兼容客户端 + `testLLM()` 四类失败的人话诊断 |
| `app/preload/preload.mjs` | `contextBridge` 白名单，与 `mock.js` 逐字段对齐 |
| `app/renderer/**` | 12 个文件、5146 行像素风界面；**无打包器、无 npm 依赖、无 CDN** |
| `runner/mcbot-gate.mjs` | 聊天门：唤醒 / owner / 限流 / 预算 / 规则路由 / 生命周期上报 |
| `runner/engine-launcher.mjs` | 组 `SETTINGS_JSON`、生成 profile、`blocked_actions` 闸门 |
| `runner/personas/**` | 6 个人格面具（中文提示词，注入引擎 `conversing` 字段的**最前面**） |
| `devtools/**` | 开发期自检工具（linkedom 渲染自检 + 假 electron 主进程自检），**不参与打包** |

## 三、唤醒与权限：实测行为表

用 `tools/test-player.mjs` 冒充真人玩家，读 `runtime/logs/<botId>.jsonl` 取证。

| 玩家 | 消息 | 门的判定 | 大模型调用 |
|---|---|---|---|
| Steve（owner） | `大家晚上好，今天天气不错` | `BLOCK rejectedNoWakeName` | **0** |
| Steve | `小豆 你好呀，能听见我说话吗` | `PASS via=llm`（cleaned=`你好呀，能听见我说话吗`） | 1 |
| Steve | `/msg Xiaodou 你在忙什么呢` | `PASS channel=whisper`（**私聊免称谓**） | 1 |
| Xiaodou（bot 自己） | `你好呀，我是小豆，我在这儿呢。` | `BLOCK rejectedSelf` | **0** |
| Alex（非 owner） | `小豆 你也来帮我建个房子吧` | `BLOCK rejectedNotOwner` | **0** |

> 门把"非 owner"放在规则之前，这条洞就没了（`docs/03` §9.3）。

## 四、一次唤醒的真实成本（T7）

这是 M1 里最值得给用户看的一个数字。用本地假大模型（`tools/mcbot-fake-llm.mjs`）返回**非零 usage**，
把 `vendor/.../src/models/mcbot.js` → 事件 → `supervisor.absorb` → IPC → 面板 整条链路打通：

```
GATE PASS via=llm <- Steve : 你好呀，再测一次
LLM response {"promptTokens":5129,"completionTokens":8,"totalTokens":5137} 4ms
GATE BLOCK rejectedSelf <- Xiaodou : 你好呀，我是小豆，我在这儿呢。
```

**一次"你好" = 5129 输入 token + 8 输出 token。** 一个 200,000 token 的日预算 ≈ 39 次唤醒。

### 4.1 这 5129 token 花在哪（实测拆解，总 10258 字符）

| 区段 | 字符数 | 占比 | 内容 |
|---|---|---|---|
| 人格提示词 | 0–1267 | 12% | 我们写的六段中文人格（`runner/personas/*.json`） |
| 引擎默认 conversing | 1267–2009 | 7% | 必须保留：里面有 `$COMMAND_DOCS` 等 6 个占位符 |
| 摘要记忆 / STATS / INVENTORY | 2009–3133 | 11% | 引擎自动填的实时状态 |
| **命令文档** | 3133–10198 | **68%** | `!COMMAND DOCS`，48 条命令的完整参数说明 |
| 示例 | 10198–末尾 | 6% | 引擎按相关度挑的对话样本 |

命令文档是大头（6999 字符 ≈ 3500 token），且**长尾分散**——最贵的 `!getCraftingPlan` 也只有 396 字符，
砍单条没意义，只能整体增删命令。

### 4.2 已经做的省钱 / 保命改动：`blocked_actions`

`commands/index.js:247` 一句 `if (agent.blocked_actions.includes(command.name)) continue;`
让 `blocked_actions` 同时是**安全闸门**和 **token 闸门**。默认清单：

```
!checkBlueprint  !checkBlueprintLevel  !getBlueprint  !getBlueprintLevel   ← 引擎默认（蓝图建造上游属实验状态）
!newAction       ← 让大模型写代码并在沙箱里跑（R-2 / R-14）
!attackPlayer    ← 陪伴型 bot 不该被一句话挑唆去打人
!restart         ← 会直接退出进程；启停是界面的职责，不该由聊天触发
```

效果（实测）：命令 51 → 48 条，提示词 10700 → 10258 字符，**5358 → 5137 token**。

### 4.3 还没用的省钱杠杆（留给 M2 决定）

- **`init_message: ''` 已经不烧开场白了**，但引擎还有个更隐蔽的坑（已修，见 §五）。
- **DeepSeek 自带前缀缓存**：提示词前 68% 是完全静态的，重复唤醒会命中缓存，实际单价远低于名义价。
  真花钱之前应该先用真 key 跑一次看 `prompt_cache_hit_tokens`。
- 命令文档可以按 **bot 的职责**裁剪（陪伴型 bot 不需要 `!tradeWithVillager`/`!clearFurnace` 这类），
  按 §4.1 的表，砍一半命令大约能省 1700 token/次。

## 五、本轮修掉的 3 个"只有真跑起来才会暴露"的 bug

### 5.1 🔴 界面永远显示"未连接"（血量却照常刷新）

`bot.on('login'/'spawn')` 注册在 `_setupEventHandlers` 里、`await originalSetup()` **之后**，
而引擎的启动顺序是 `Xiaodou logged in!` → `Xiaodou spawned.` → 我们才装上监听器 →
**这两条一次性事件被整个错过**，`runtime/logs/*.jsonl` 里 57 条 `mc` 全是 `kind:"stats"`，一条 `login`/`spawn` 都没有。

修法（两道保险，都必要）：
1. `mcbot-gate.mjs` 装好监听器后**立刻按当前真实状态补发**一次：`if (bot.username) emit('mc',{kind:'login',replay:true})`、`if (bot.entity) emit('mc',{kind:'spawn',replay:true})`。
2. `supervisor.mjs` 的 `absorb` 让 `kind==='stats'` 也置 `mc.connected = true`——心跳能到就是连着。

### 5.2 🔴 引擎自己重启 agent 时会烧掉一次调用，还让 bot 自己开口说话

`agent_process.js:49/77/81` 在 agent 子进程崩掉后会带一句
`init_message = 'Agent process restarted.'` 重启它，那句走 `agent.js:214` 的 `handleMessage('system', …)` →
**一次真实的大模型调用**，而且 bot 会在没人叫它的情况下自己说话。

实测抓到过（`.spike/fake-llm.log` 里 `2026-10-05T10:43:01Z` 那条 chat 请求的 content 就带着这句话）。

修法：门包装 `Agent.prototype.handleMessage`，**精确掐掉这两句引擎内部口令**，
其它 `system` 消息一律放行（那些是"动作被打断""你死了"之类的反应式通知，掐了 bot 会变聋）。

### 5.3 🟡 迟到的 `status:"starting"` 把界面打回"启动中"

启动器（父进程）和聊天门（agent 子进程）**各写各的事件到同一个 jsonl**，时间戳同秒、顺序可能颠倒，
实测出现过 `running` 之后紧跟一条"引擎进程已启动"。修法：`supervisor.mjs` 的 `case 'status'` 里，
已经在线的 bot 不接受回退到 `starting`。

### 5.4 🔴 我的测试脚本把你的配置改坏了（这条是流程教训，不是引擎的坑）

**现象**：`runtime/config.json` 里三个模型全指向 `http://127.0.0.1:8799/v1`、
`model` 全变成 `mcbot-spike-model`，还多出一个测试用的 bot —— 你打开应用会以为自己的 API 地址坏了。

**成因链**（三步，每一步单独看都不像错）：

1. 自检第 9 节要起真引擎，而 supervisor 是**从磁盘读配置**的，所以必须把配置真的落盘成"指向本地假模型"。
2. 我按常规写了"开头整份备份 → 跑完无条件还原"，还额外挂了 `process.on('exit')` 兜底。
3. **但我是这样跑它的**：`... | Select-Object -First 20` —— 只想看前半段输出。
   PowerShell 一关管道就把 node 硬杀了（TerminateProcess），**`finally` 和 `process.on('exit')` 都跑不到**。

**修法**：不再依赖"记得还原"这种纪律，改成**物理上够不着**。在 `app/electron/paths.mjs` 里
把路径拆成两个概念：

| 常量 | 是什么 | 能不能重定向 |
|---|---|---|
| `RUNTIME_HOME` | 随应用分发的东西：Node 运行时、Java、测试服 | ❌ 不能 |
| `RUNTIME_DIR` | **用户数据**：`config.json` / `secrets.json` / `logs` / `tmp` | ✅ `MCBOT_RUNTIME_DIR` |

新增 `devtools/sandbox-env.mjs`，作为自检脚本的**第一个 import**（ESM 按声明顺序求值，所以它一定先跑）：
它把用户真实配置**拷一份**到 `runtime\tmp\sandbox-selftest\`，然后把 `MCBOT_RUNTIME_DIR` 指过去。
自检改的、写的、删的全在沙箱里，跑完还会用 SHA256 断言用户的 `config.json` 与 `secrets.json`
**一个字节都没变**。

**顺手暴露的第二个问题**：我第一版只加了 `RUNTIME_DIR` 的重定向，结果 `findNodeRuntime()`
去沙箱里找 Node —— 当然找不到，`supervisor.start()` 于是返回 `{ok:false, errors:[…]}`，
而我的测试只打印 `.error`，屏幕上只有一句没头没尾的 `start(bot-xiaodou) 失败：undefined`。
**一个变量干了两件事**，就是这个错误的全部原因。

**另一个同源问题**：`app/electron/main.mjs` 自己又拼了一份
`const RUNTIME_DIR = path.join(PROJECT_ROOT, 'runtime')`，绕开了 `paths.mjs`。
已改成从 `paths.mjs` 导入 —— "全应用只有一个路径来源"这条约定一旦破口，沙箱隔离就漏了。

> **这条值得单独记住**：凡是会自动修改用户文件的测试，安全性不能建立在"清理代码一定会被执行"上。
> 进程可能被硬杀（管道截断、超时、任务管理器），任何 `finally` 都指望不上。
> 唯一的保证是让它从一开始就够不着用户的文件。

## 六、我为什么没能亲眼看到窗口（以及你怎么看）

**这台执行环境起不来 Electron，与你的电脑无关。**

- DSH 自己给子进程注入了 `ELECTRON_RUN_AS_NODE=1`（DSH 本体就是 Electron 应用），
  直接跑 `electron.exe` 会退化成纯 Node——`electron.exe --version` 打印的是 `v24.21.0` 而不是 `v44.5.1`。
- 清掉该变量后，一个最小 Electron 应用（`app.whenReady()` 后只 `console.log`）**仍然崩溃**，
  退出码 `0x80000003`（STATUS_BREAKPOINT）/ `0xC0000005`（ACCESS_VIOLATION）。
- 试过 `--no-sandbox`、`--disable-gpu`、`--in-process-gpu`、`--disable-crash-reporter --disable-breakpad`、
  `cmd /c` 重定向、`Start-Process -Wait`，**并且用 `danger-full-access` 提权重试过一次**——全部照崩。
  → 不是文件沙箱的问题，是这个执行环境（父进程 Job 对象 / 无交互桌面会话）不允许 Chromium 起来。
- 安装本身是好的：`app\node_modules\electron\dist\` 完整，`electron.exe` 245,726,208 字节，
  SHA256 `49B61A030A520FC36A4B8FA5CCE53FB4E935A7BDBBE4B80E9222F598E49CC7FA`，`version` 文件写 `44.5.1`。

**替代验证（我做了）**：两套无头自检，把"窗口之外的一切"都真跑了一遍。

| 工具 | 命令 | 覆盖面 |
|---|---|---|
| `devtools/render-headless.mjs` | `node devtools/render-headless.mjs` | linkedom 真装载 12 个渲染文件、逐个点击 **8** 个导航页并断言渲染字符数 |
| `devtools/headless-main.mjs` | `node --import ./devtools/register-electron-stub.mjs devtools\headless-main.mjs` | 假 electron 模块 + 55 项检查：配置/密钥/环境/LLM 客户端/IPC 契约（**25** 个 channel）/事件通道/参数翻译 |

加上真实引擎那一节（`MCBOT_HEADLESS_REAL_ENGINE=1`）共 **63 项全绿**。
这一节**等于把你要做的第 1、4 步先替你走了一遍**：主进程真的 `spawn` 了一个引擎子进程、
bot 真的登录了 1.21.1 服务器、`stop()` 真的干净收尾且不触发退避重连。


## 七、多 bot / 多服务器并行：把核心需求的另一半也验掉

> 用户的原始需求里写的是"**可多服务器并行**"。单 bot 那条线早就验过了，但
> "两个 bot 同时在线"和"两个 bot 分处两台服务器"从来没验过——而它们恰好踩在几个已知风险上。
> 两个新脚本 **`headless-multibot.mjs`（34 项）** 与 **`headless-multiserver.mjs`（29 项）** 全绿。

### 7.1 为什么要单独写一个脚本

| 风险 | 为什么单 bot 测不出来 | 实测结果 |
|---|---|---|
| **MindServer 端口冲突** | 引擎每个 bot 一个进程、每个进程自带一个 MindServer。上游默认写死 8080 | ✅ 散列分配生效：`bot-xiaodou` → **8266**、`bot-axiao` → **8249** |
| **唤醒串台** | 同一服务器上两个 bot，叫 A 的时候 B 会不会也应答 | ✅ 全程零串台（见 7.2） |
| **事件串台** | 两个 bot 各写一条 jsonl，界面靠文件名区分 | ✅ `bot-xiaodou.jsonl` / `bot-axiao.jsonl`，两个独立 pid |

还有一条是 `docs/03` §9.2 记录过的**上游地雷**，这次专门来证伪：

```js
// vendor/mindcraft-develop/src/agent/agent.js —— 引擎原文
this.bot.on('chat', (username, message) => {
    if (serverProxy.getNumOtherAgents() > 0) return;   // 有别的 agent 就整体关掉公屏
    respondFunc(username, message);
});
```

**结论：这颗雷对我们无效。** 原因有两层——① 每个 bot 有独立的 MindServer，各自视角里
"其他 agent 数"都是 0；② 更根本的是，我们的门在 `_setupEventHandlers` 之后**把引擎那两条
`chat`/`whisper` 监听器摘掉了**（`removedEngineListeners=2`），那颗地雷连同它的守卫一起被移除，
换成我们自己的门（公屏需称谓、私聊免称谓）。实测两个 bot 都完整收到了公屏每一句话。

### 7.2 唤醒隔离实测（Steve 一个人说话，两个 bot 都在线）

| 玩家说 | 小豆（A） | 阿霄（B） |
|---|---|---|
| `大家晚上好，今天天气不错` | `BLOCK rejectedNoWakeName` | `BLOCK rejectedNoWakeName` |
| `小豆 你好呀` | ✅ `PASS via=llm` | `BLOCK rejectedNoWakeName` |
| `阿霄 你好呀` | `BLOCK rejectedNoWakeName` | ✅ `PASS via=llm` |
| `/msg Xiaodou 在忙吗` | ✅ `PASS channel=whisper`（免称谓） | 完全没被唤醒 |

**两个 bot 都听见了每一句公屏，但只有被叫到名字的那个才烧 token。** 这正是设计意图。

### 7.3 顺手抓到的两件事

**① bot 之间会互相触发一次门禁判定（零 token，但有日志）**

`bot-axiao` 自己说的话，在 `bot-xiaodou` 那边被记成 `BLOCK rejectedNotOwner from=Axiao`。
这是**对的行为**（阿霄不在小豆的主人名单里），但意味着：服务器上每多一个 bot，其余每个 bot
都会多一条"别人的话"的判定记录。零 token 成本，纯粹是日志噪音。M2 可以考虑把
"服务器上已知的其他 bot 名字"加进一个静默名单。

**② 一次唤醒成本交叉验证通过**

A 本次放行 2 次、累计 **10311 tokens** → 平均 **5155 token/次**，与 §四 独立测得的 5137 吻合。
两个完全不同的测法得到同一个数，说明这条计数链路是真的。

### 7.4 顺带修掉的一个界面瑕疵

第一次跑通时看到 `connected=true` 但 `health=null position=null`——因为状态上报是
10 秒一次的心跳，**刚上线的那一瞬间面板是空白的**。已在 `runner/mcbot-gate.mjs` 里
把上报逻辑提成 `emitStats()`，装上监听器后**立刻先发一条**，再进 10 秒定时。
现在实测连上的同一刻就已经是 `血量=20 位置={"x":-8.5,"y":119,"z":5.5}`。

### 7.5 还能往下关掉的一个：单独关 B 不影响 A

`stop(B)` → B 干净停止且未触发退避重连，**A 仍在线且血量正常**。这条是多 bot 场景的底线：
不能出现"关一个带崩一片"。

### 7.6 多**服务器**并行：另起一台服，真跑一遍

§7.1–7.5 的两个 bot 都在**同一台**服务器上。但用户要的是"**多服务器**并行"——
那是另一条代码路径（每个 bot 走自己的 `serverId`）。所以我又起了一台测试服：

```
25565  testserver\    第一台（原版 server.jar）
25566  testserver2\   第二台（原版 server.jar，新建，level-name=world2）
```

> 顺带踩到一次**已知坑**：第二台一开始想用 `fabric-server-launch.jar` 起，崩在
> `IOException: the jar file .\.fabric\remappedJars\...\server-intermediary.jar.tmp can't be written`
> —— 就是 README「已知坑」里那条"沙箱给工作区文件打完整性标签，Java 的 `Files.isWritable()` 误判"。
> 改用纯原版 `server.jar` 立刻起来。

`devtools/headless-multiserver.mjs`，**29 项全绿**。关键证据：

| 断言 | 实测 |
|---|---|
| 两个 bot 绑在不同服务器 | A → `srv-local`(25565)、B → `srv-test2`(25566) |
| **引擎自己报告的连接目标**（最硬的证据，从 `<botId>.out.log` 里读 `MC server found.`） | A → `127.0.0.1:25565`、B → `127.0.0.1:25566` |
| 两台服务器各自的自报在线人数 | 各 **1/10** —— 确实各连一台，没有都挤到同一台 |
| 两个 bot 的**世界坐标无关** | A 在 `(-8.5,119,5.5)`、B 在 `(-275.5,71,-609.5)`（各自独立生成的世界） |
| **跨服务器唤醒隔离** | 在服务器 B 上喊"小豆" → A **完全没被唤醒**（它在服务器 A 上，收不到 B 的公屏） |
| 同服内唤醒照常 | 在服务器 B 上喊"阿霄" → B 正常放行 |
| 跨服零 token 泄漏 | A 全程 **0 次**大模型调用，B 的每次放行都对应一次调用 |
| 关掉 B（在服务器 B） | A（在服务器 A）**仍在线、血量正常** |

**这条是用户需求里最关键的一半，至此有了实测证据。**

## 七·补、中文采集指令：把"帮忙搜集原材料 / 一起探险"做成真的

> 这一节是 M1 交付**之后**追加的。用户 m00001 的原始需求里写着"搜集原材料、一起探险"，
> 而 M1 的 A1–A6 只覆盖到聊天与跟随 —— 这条缺口在这里补上。
> 补它的成本极低，因为"规则命中 → 直接发引擎命令"这条**零 token 通路**在 A3（跟着我）里已经验过了。

### 7b.1 问题的真正难点在哪

引擎有 `!collectBlocks(type: BlockName, num: int)`，看起来只要加一条规则就完事。
但它有两个中文用户必然撞上的硬边界（详见 `docs\03` §十）：

1. **`BlockName` 是精确匹配的英文 id**。`src/agent/commands/index.js` 拿 `getBlockId(arg)` 校验，
   中文进去必然得到 `Invalid block type: X.`。引擎侧没有任何中文能力 —— **翻译只能在我们这层做**。
2. **石头和矿物必须有镐子**（`skills.js:490` 的 `block.canHarvest()`），没工具会直接放弃并
   在聊天框里丢一句英文 `Don't have right tools to harvest stone.`。

### 7b.2 我们做了什么

- **`runner\vocab.mjs`（新）**：中文意图词典 + 数量解析 + 方块消歧。37 条词条覆盖原木/石料/9 种矿物/农作物。
  设计原则写在文件头：**宁可认不出（返回 `null`，退回大模型），也不要猜错** ——
  猜错的代价是 bot 兴冲冲跑去挖一堆用户没要的东西。
  词索引**按词长降序**排，保证「钻石」不被「石」抢走、「铁矿石」不被「铁矿」抢走。
- **三条新内置规则**（`collect` / `seek` / `explore`），写在 `app\electron\store.mjs` 的 `DEFAULT_RULES`，
  与 `runner\bots\xiaodou.launch.json` 同步。
- **`migrateConfig()`（新）**：老配置里已经有那 5 条规则，`normalizeConfig` 不会补新的 ——
  所以加了只增不改的迁移，否则老用户升级后会觉得"功能没做出来"。实测两个 bot 都被补上了 3 条。
- **`FALLBACK` 判定**：规则话头命中但参数认不出（"帮我弄点那个"）时，**退回大模型**而不是瞎猜。
  这是一个新的门禁判定档，`supervisor` 与界面日志都单独计一档。
- **`preflightCollect()`（新）**：采集前检查手里有没有镐子，缺了就用中文回话，
  而不是把引擎那句英文原样丢给用户。
- **主人直接敲 `!命令`**（"小豆 !inventory"）：引擎原本对**任何人**都执行 `!命令`，
  我们收紧成"只有主人能敲"，但**刻意保留这条通路** —— 它零 token、零延迟，
  而且 48 条引擎命令因此全部对用户可用。透传前先过 `commandExists()`，
  否则会绕过 `blocked_actions`（`executeCommand` 自己不看这个字段）。

### 7b.3 真实 1.21.1 服上的实测（全部通过）

| 玩家说 | 门的判定 | bot 实际做了什么 |
|---|---|---|
| `小豆 去砍点木头` | `PASS via=rule cmd=!collectBlocks("oak_log", 10)` | **真的砍回 10 个橡木**（背包：`oak_log:10 oak_sapling:2 stick:5`） |
| `小豆 !inventory` | `PASS via=command` | 聊天框回 `INVENTORY - oak_log: 10 …` |
| `小豆 挖点石头` | `PASS via=rule-guard` | 回**中文**：「我手里没有镐子，石头挖不动呀。你先给我做一把木镐（三个木板加两根木棍），我马上就去。」 |
| `小豆 附近有没有铁矿` | `PASS via=rule cmd=!searchForBlock("iron_ore", 64)` | 定位成功：`Found iron_ore at (-4, 108, 2)`；但走过去要挖开石头 → `Cannot break stone with current tools` |
| `小豆 四处走走` | `PASS via=rule cmd=!moveAway(30)` | 从 `(-4, 112, 1)` 走到 `(-32, 116, -11)` |
| `小豆 帮我弄点那个` | `FALLBACK ruleUnresolved` → `PASS via=llm` | 交给大模型，正常中文回复 |

**整轮的门禁账本：放行 9 / 拦下 11，大模型只调用了 1 次（5104 token）。**
也就是说"采集原料"这件事的实际 token 成本是 **0**。

### 7b.4 诚实的边界（要告诉用户的话）

- **木头、泥土、沙子用手就能采**，空手出生的 bot 立刻可用。
- **石头、圆石、各种矿物必须先有镐子**。这是 Minecraft 自己的规则。
  bot 现在会用中文告诉玩家缺什么、怎么补，但**它不会自己去合成镐子** ——
  那需要串起"砍木头→做工作台→做木镐"三步，属于 M2 的"建造/合成"能力。
- `四处走走` 只是 `!moveAway(30)`，即"朝任意方向走开 30 格"，**不等于真正的探索**。
  引擎没有"探索"这个原语；真正的探索要自己写（选方向、避危险、记路、回来），属于 M2。

### 7b.5 怎么复现

## 七·补二、盖房子：用户四项能力里最难的那一项

用户 m00001 列了四项能力：聊天互动 ✅、接受聊天框指令 ✅、陪同探险 ✅（`四处走走`）、
采集原料 ✅（`去砍点木头`）。**"帮忙建房子"是唯一一项当时还完全没有的** —— 这一节记它怎么落地的。

### 7c.1 先查引擎：它**一点建造能力都没有**

把 `vendor/mindcraft-develop/src/agent/commands/` 翻了个遍：

- 动作命令 41 条（`!goToPlayer` `!collectBlocks` `!craftRecipe` `!placeHere` …）、
  查询命令 14 条（`!stats` `!inventory` `!getBlueprint` …）。
- **没有 `!build`，没有任何"盖一栋房子"的命令。**
- 最接近的是 `!placeHere(type: BlockOrItemName)`，但它的官方描述**明确禁止**拿它盖建筑：
  `Do NOT use to build structures, only use for single blocks/torches.`
  实现就是一次性调 `skills.placeBlock(bot, type, pos.x, pos.y, pos.z)`。
- 引擎**确实自带**一套分层蓝图系统（`src/agent/tasks/construction_tasks.js`，42,921 字符，
  含 `class ConstructionTaskValidator`），但它**只能由大模型通过 `!newAction` 写代码来驱动** ——
  而 `!newAction` 是我们的安全红线（已进 `blocked_actions`：模型写的代码绝不在本机执行）。
  `!checkBlueprint` / `!getBlueprint` 都是只读查询，不会动手盖。

**结论：建造必须长在我们这一层。** 但**不自己实现放方块** —— 引擎的
`src/agent/library/skills.js:611 placeBlock(bot, blockType, x, y, z, placeOn='bottom', dontCheat=false)`
已经处理好了所有脏活：自己清掉挡路的方块（`breakBlockAt`）、自动找相邻实体方块当支撑面
（`buildOffBlock` + `faceVec`）、太近（<1.1 格）会后退、太远（>4.5 格）会走过去、
最后 `equip(item,'hand')` + `lookAt(...)` + `placeBlock(...)`。

### 7c.2 我们这一层做什么：`runner\builder.mjs`

| 职责 | 实现 |
|---|---|
| 把一栋小屋拆成**有序**方块列表 | `hutPlan(spec)` → `[{x,y,z,block}]`，相对坐标，原点在西南下角地面那层 |
| 顺序即正确性 | 墙按层（y 从低到高）、屋顶从西南角按行铺 —— **保证每块放的时候底下或旁边已经有东西**（`placeBlock` 找得到支撑面） |
| 尺寸 | `HUT_PRESETS = { small: 3×3×2, big: 5×5×3 }`，`w<3`/`h<2` 直接抛错（放不下门） |
| 门 | `isDoor(x,y,w)` = `y < 2 && x === floor((w-1)/2)` —— 只在**南面**开一个 2 格高的门洞 |
| 材料核算 | `countMaterials` / `checkMaterials` / `countInInventory`，木板不够但有原木 → 返回 `{canCraft:true, craftFrom, craftTimes}` 让我们自己合成 |
| 选址 | `findGroundY` + `findBuildSite`（见 7c.4） |
| 逐块执行 | `runBuild(agent, plan, origin, onProgress, skills)`，每块前检查 `bot.interrupt_code` |

规则接入在 `runner\mcbot-gate.mjs`：`rule.action === 'buildHouse'` 时整条走本地流程，
**零 token**；`app\electron\store.mjs` 里对应第 9 条默认规则 `build`（话头 `盖个房子` `建个房子`
`搭个房子` `造个房子` `盖个小屋` `帮我盖` …）。

### 7c.3 🎉 真机结果：一栋 23/23 的房子，外加**独立取证**

### 7c.4 一路上踩掉的四个真 bug（都不是笔误，都是设计漏洞）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 屋子**两头通**，`small` 算出 21 块而不是 23 块 | 南面 `z=0` 与北面 `z=d-1` 共用了同一个 `if (!isDoor(...))` 守卫，门被开了两次 | 北面那次 push 去掉 door 守卫；单元测试加了"北面必须是整堵墙"的断言 |
| 2 | `TypeError: pos.floored is not a function`（`prismarine-world/src/worldsync.js:102`） | `findGroundY` 给 `bot.blockAt()` 传了**普通 `{x,y,z}`**，而世界层要的是 Vec3 实例 | 新增 `vecAt(bot,x,y,z)`：从 `bot.entity.position.constructor` 借 Vec3 构造器。**当时的 18 项单元测试全绿也照不出来**（假 bot 不挑参数），于是把假 bot 改成**故意按真实世界层挑食**，作为回归测试 |
| 3 | 只盖到 **20/23**，失败处报 `The goal was changed before it could be completed!` | 盖到一半来了只**僵尸**，引擎切去战斗，pathfinder 的目标被抢走 | `runBuild` 加一次**补放**（`missing` 数组，`!interrupted && missing.length` 时对失败的方块再来一遍），返回体加 `missing` |
| 4 | 第二次盖房只得 **18/23**，`placeBlock` 连着 5 次报"放不上去" | 上一栋房子还在 `(-13,112,-4)`，新一轮选址挑了 `(-12,112,-5)`，**两块地重叠 2×2 格**。四角齐平（旧墙顶也是平的），但中间杵着旧墙 | 选址从"查四角"升级为**查整个 footprint 的每一列**（`columnClear`：地面在本层或下一层 + 上面 h+1 格全空）。顺带修掉一个更隐蔽的：缓坡上 3×3 的**四个角 x 坐标同奇偶**，四角永远一样高，中间那列反而更高 —— 地基必须取**整块地**的最高层，不能取四角的 |

另外两处不是 bug 但同样致命的：

- 🔴 **`.catch(() => {})` 吞掉异常**（`runner\mcbot-gate.mjs:530-531`）。建造任务抛异常后
  **整个流程静默消失**：日志里既没有"开始盖房"也没有任何报错，stderr 只有
  `keys.json not found. Defaulting to environment variables.`，白查半小时。
  改成 `onFailure(err)`：`console.error` + `emit('error', {where, message, stack})`。
  **教训：吞异常的 catch 是最贵的代码。**
- 🔴 **合成一次补不齐**。`checkMaterials` 算的是"差多少就合多少"，但引擎
  `skills.js:103` 是 `bot.craft(recipe, Math.min(craftLimit.num, num), craftingTable)`
  —— 原木不够时它会**少合几次就返回**；而 `canCraft` 分支当时返回 `message: ''`，
  于是玩家看到的是半截话「盖房材料不足：」。改成**循环补齐**（最多 8 轮，每轮等 600ms
  让背包同步），并给 `canCraft` 分支补上兜底话术。修好后实测
  `自动合成 oak_planks ×5 次（6 → 26 块）`。

### 7c.5 诚实的边界

- 房子是**固定两种尺寸的方形小屋**（3×3、5×5），不是"按玩家描述自由设计"。
  自由设计要么靠蓝图（引擎那套要 `!newAction`，被我们的红线挡住），要么 M2 自己做。
- 材料只用**木板**（原木自动合成）。"用石头盖"理论上走 `parseCollectIntent` 认建材，
  但石头需要镐子 —— 与 7b.4 同一条边界。

  「我在你旁边没找到一块四角一样平的场地，你带我找块平整的草地吧。」
- 盖完不会**开门**（放的是门洞，不是 `oak_door`）；也不会自己造床、火把、箱子。

## 七·补三、一起探索：从"逃跑"升级为"真探险"

### 7d.1 改写的原因：原来那个不是探险

在这之前，"四处走走"命中的是引擎的 `!moveAway(30)` —— **朝任意方向走开 30 格**。
它确实会让 bot 移动，但走完它什么都不知道、也说不出一句话。用户 m00001 要的是
"**一起探索**"，一个走完不作声的 bot 不叫陪玩。**那不是探险，那是逃跑。**

引擎里没有任何"探索"原语（`docs/03` §十 已核验过全部 55 条命令），所以这一层只能自己写。

### 7d.2 我们做了什么：`runner\explorer.mjs`

和建造器同一套分工原则：**不重写寻路**，用引擎的 `skills.goToGoal(bot, goal)`
配上 mineflayer-pathfinder 的 **`GoalXZ`**。选 `GoalXZ` 而不是 `GoalNear` 是有原因的：
野外目标点的实际地面高度无从得知（远处区块还没加载，`blockAt` 返回 null），
用三维距离会让 pathfinder 在"差 8 格高度"的地方反复横跳直到超时。

三条设计原则写在文件头：

1. **不往水里跳**：挑方向时检查目标那一列，读到 `water/lava/powder_snow/fire/magma_block/cactus`
   就换一个方向；试 3 个方向都不行就老实说"不是水就是岩浆，没地方好去"。
   ⚠️ 但**区块没加载（`blockAt` 返回 null）必须放行** —— 远处读不到不等于有危险，
   当成障碍会让 bot 永远不敢出门。
2. **一定要能回来说话**：单程有上限，报告完还要走回玩家身边。
3. **说不出发现就是白走**：结束时必须报出"走了多远、到了哪、看见了什么"三要素。

`scanAround(bot, r=16, dy=6)` 扫 33×13×33 ≈ 14k 格（几十毫秒），按一张 `NOTABLE`
正则表挑出值得说的东西（钻石/绿宝石/铁矿/煤/树/水/岩浆/花/村庄……顺序即汇报权限）。
**水和沙子会被从"发现"里剔掉** —— 脚边一条河不算探险收获。
群系读取做了三级兜底，**读不到群系绝不让整趟探险判失败**。

### 7d.3 真机结果

第一次跑就暴露了一个真问题：

```
20:00:25  出发探险：往东南 48 格 → (13, 25)
20:02:56  探险结束：那边太远了，我走了 26 格还没到，就先回来了，
          现在在 (-2, 119, 10)，一路上看见了树×153、铁矿×20。
```

汇报链是对的，但**48 格走了 150 秒只挪了 26 格** —— 一次 `GoalXZ` 拉 48 格穿过森林，
pathfinder 在复杂地形里反复重算，几乎原地打转。

改成**分段短跳**（`HOP_MAX = 16` 格一段，每段 30 秒上限，段间重新算一次路）之后：

```
20:06:05  出发探险：往西 32 格 → (-35, 9)
20:06:05  <Xiaodou> 好，我往西走走看，最多 32 格，回来告诉你看见什么。
20:06:11  探险途中：走到 (-27, 119, 10)
20:06:14  探险结束：我往西走了 32 格，现在在 (-34, 116, 9)，一路上看见了煤矿×132、铁矿×38。
20:06:14  探险归来：距离你 25 格，往回走
20:06:22  已回到你身边（走了 24 格）
20:06:22  <Xiaodou> 我回来了。
```

**同样 32 格，9 秒走完（原来是 150 秒走 26 格）。** 而且三要素齐全、还自己走回来了。
整轮零 token —— 走的是"规则命中 → 本地流程"的通路。

### 7d.4 一路上踩掉的三个真 bug

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| D1 | `ReferenceError: say is not defined`（真机第一次跑就炸） | `say` 定义在 `runBuildTask` **内部**，探险一调就找不到 | 抽成 `makeSayer(agent, username)`，两个任务各自取用。**`node --check` 完全看不见这类错误** —— 是上一轮修的 `onFailure` 把它抓出来的 |
| D2 | 超时保护永远不触发，测试报 `Warning: Detected unsettled top-level await` | 超时定时器加了 `unref()`，当"唯一还在等的就是它"时 Node 直接退出 | 守卫定时器**不 unref**（它就该拖住进程）；进度上报的 `setInterval` 保持 `unref` |
| D3 | 玩家喊"停下"之后，走了半路的探险被报成"走完了" | **寻路库被 stop 之后不一定抛错**，有的版本安静停下、`goto` 照常 resolve | `interrupt_code` 置位后无论走没走完都返回 `reason='interrupted'`；轮询从 3000ms 收紧到 1000ms |

D3 是最值得记的一条：**代码在跟玩家撒谎**，而且撒得很自然 —— 只有把"停下"的实测
跑一遍才会发现。另外单测里那条 `找不到方向时不能假装走了一趟`（目标就是脚下 → `no-target`）
也是同一个思路。

### 7d.5 诚实的边界

- 探索范围上限是 **80 格**（默认 32）。要真正"远征"得先解决跨区块寻路与沿途记路。
- **不会挖矿**：会告诉你"那儿有铁矿"，但挖石头需要镐子（与 7b.4 同一条边界）。
- 不做"回去的路标"：回程是照着玩家当前位置重走一遍，不是记住来时的路。
- 一次只走一个方向，不会自己规划"绕一圈看看"。

## 七·补四、长期陪伴记忆：让 bot 真的"记得住"

### 7e.1 先说清楚：引擎那份"记忆"为什么不能用

`vendor\mindcraft-develop\src\agent\history.js` 里确实有个 `memory` 字段，看起来正合用。
打开看是这么回事：

| 事实 | 原文 / 位置 | 意味着什么 |
|---|---|---|
| 硬上限 500 字符 | `if (this.memory.length > 500) { slice(0,500); += '...(Memory truncated to 500 chars. Compress it more next time)' }` | 记得住的量是固定的，跟相处多久无关 |
| 重写要调大模型 | 每攒够 `settings.max_messages` 条就 `promptMemSaving(turns)` | **记忆本身是要花钱的**，而且每次重写都可能把旧事压掉 |
| 我们启动时 `load_memory: false` | `runner\engine-launcher.mjs` 的 SETTINGS_JSON | **重启一次记忆就归零** |

结论：**那是"为了省 token 压缩上下文"用的，不是陪伴用的。** 硬塞更多进去只会推高每次唤醒的成本。
所以这一层得我们自己起。

### 7e.2 `runner\memory.mjs` 做了什么

一份纯 JSON 的长期记忆，落在 `runtime\memory\<botId>.json`（**不在引擎的 `bots/<name>/` 目录里** ——
那是引擎自己的地盘，`npm install` 或换引擎版本都可能被动过）。

- **四种记忆**：`fact`（事实）、`promise`（约定）、`place`（地点）、`event`（经历）。
- **中文检索用二元组**：中文没有空格，按字切会把"钻石"拆成两个没意义的字。
  二元组 + 一张忽略表（什么/怎么/这个/一下/记得/知道…），否则"这是什么"会匹配上一切。
  打分 = 命中的检索词数（二元组权重 2、单字 1），**直接包含原句再 +6**。
- **约定永不被挤掉**：超过 `MAX_ENTRIES = 80` 条时丢最旧的，但 `promise` 优先保留 —— 欠人的话不能忘。
- **摘要不假装完整**：`digest()` 截断时补一行「• …（还有更多，问我具体的）」。
- **落盘是原子的**：写 `.tmp` 再 `renameSync`；文件坏了返回空记忆，**绝不抛**。
- **设计原则写在文件头**：宁可漏记也不要把闲聊灌进去 —— 记忆一旦变噪音，比没有更糟。

### 7e.3 三条入口，两条零 token

| 玩家说 | 谁处理 | 成本 |
|---|---|---|
| `记住我喜欢钻石` | 规则命中 → 本地写入 | **0** |
| `你还记得我喜欢什么吗` | 规则命中 → 本地检索 | **0** |
| 闲聊里夹带长期信息 | 走大模型，**但顺手记下来** | 一次正常唤醒 |

第三条是 `injectMemory()`：只在 `memory.recall()` 命中时才往 history 里塞
`【你记得的事】`，**只塞相关的、不无脑全塞 —— 那都是钱**。整个过程套在 try/catch 里，
**记忆出问题绝不能挡住正常对话**。

此外建造与探险结束时会 `recordEvent()` 主动记一条经历（"在 (x,y,z) 盖了一栋3×3 的小木屋"），
也是零 token。

### 7e.4 🎉 真机实测（同一台 1.21.1 服，Steve 依次说四句）

| 玩家说 | 门禁判定 | bot 回 |
|---|---|---|
| `小豆 记住我喜欢钻石` | `PASS via=rule rule=remember cmd=<本地记忆读写>` | 「记住了：我喜欢钻石」 |
| `小豆 你还记得我喜欢什么吗` | `PASS via=rule rule=recall` | 「我记得：我喜欢钻石」 |
| `小豆 我家在 (-12, 64, 30)，以后别在晚上出门` | `PASS via=llm` + 日志 **`顺手记住：我家在 -12 64 30 以后别在晚上出门`** | 假模型固定回复 |
| `小豆 你还记得我家在哪吗` | `PASS via=rule rule=recall` | 「我记得：…」 |

整轮账本：`事件类型 {"log":5,"status":4,"mc":9,"gate":8,"llm":2}`
—— **四句话只花了 1 次大模型调用**（第三句），其余三句零 token。

### 7e.5 一路上踩掉的四个真 bug

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| E1 | `你记得什么` 跑去检索"什么"两个字 | 通配正则排在"你记得什么/啥/多少/哪些"**前面** | 把那几条**提到最前**；顺带写下"顺序即语义" |
| E2 | `memoryFileFor('../../etc/passwd')` 洗出 `.._.._etc_passwd`，**`..` 还在** | sanitize 只替了路径分隔符 | 追加 `.replace(/\.{2,}/g, '_')` |
| E3 | 一句里说两件事被存成一条囫囵话：「我家在 -12 64 30 以后别在晚上出门」 | `norm()` 把标点吃掉后才判断，整句进了同一格 | `extractFacts` 改成**先按标点切短句再逐句判断**，一条消息最多记两句 |
| E4 | 切句之后**坐标被剁碎**：日志里赫然一行「顺手记住：我家在 **-12**」，y 和 z 没了 | 坐标三元组里的逗号也是逗号，按 `,` 切句必然把 `(-12, 64, 30)` 切成三截 | 切句**之前**先用占位符把坐标三元组护起来，切完再换回来；顺带把带坐标的那条标成 `place`（界面上显示"地点"标签） |

- **E3 和 E4 都是真机上看出来的，单元测试全绿也没用** —— 因为断言只检查"记下了没有"，
  不检查"记下来的读着像不像人话"。E4 甚至是**修 E3 才引出来的新 bug**：
  两个修复叠在一起才暴露，说明"改一处、看一处"不够，改完必须再真机跑一遍。
- E4 修完的实测（同一条消息、同一个玩家）：
  ```
  >>> chat: 小豆 我家在 (-12, 64, 30)，以后别在晚上出门
  >>> chat: 小豆 你还记得我家在哪吗
  <chat> <Xiaodou> 我记得：我家在 -12 64 30          ← 三个数一个不少
  记忆文件：- place "我家在 -12 64 30"
            - fact  "以后别在晚上出门"                 ← 两条分开了
  ```

### 7e.6 诚实的边界（要告诉用户的话）

- 记忆是**单 bot 独享**的，同一台服上两个 bot 不会共享（`runtime\memory\<botId>.json` 分开）。
- **不会自己判断什么值得记**：只有明确的"记住……"和一小撮句式（`FACT_MARKERS`）会被自动捞。
  宁可漏，不灌噪音。
- 检索是**关键词匹配，不是语义理解**。问"我上次说喜欢什么"能中，问"我有什么偏好"大概率中不了。
- 80 条封顶。满了会丢最旧的，但**约定（`promise`）优先保留**。
- 坐标读回来是 `-12 64 30` 这种空格分隔的样子（标点被规整掉了），**在 Minecraft 语境里不影响理解**，
  但不要指望它原样保留括号。

## 七·补五、合成链：让"挖点石头"真的能挖到

### 7f.1 起因：一句"我没有镐子"把玩家的期待截断了

`采集原料` 这条能力在 §7b 就通了，但它有一条硬边界：

> 玩家说 `小豆 挖点石头` → bot 回「我手里没有镐子，石头挖不动呀。你先给我做一把木镐。」

**这句回话在功能上没错，在产品上错了。** 玩家说"挖点石头"，期待的是一会儿石头到手，
而不是被派去做镐。真正的陪伴是 bot 自己想办法：砍两根木头 → 削木板 → 搭工作台 → 做木镐 → 去挖。

而引擎这边根本没有"做一把镐"这种命令 —— `!craftRecipe(item_name, num)` 只会做**一步**，
且 `num` 是"合成次数"不是产出件数。串链只能长在我们这层。

### 7f.2 引擎的 `craftRecipe` 有三处必须知道的行为

一手读自 `vendor\mindcraft-develop\src\agent\library\skills.js:36-113`：

| 位置 | 行为 | 对我们的影响 |
|---|---|---|
| `skills.js:61-76` | 没有工作台时会去 16 格内找；背包里有台子就找块空地放下去；两样都没有 → `return false` | 我们不用自己管工作台，但要**把"要 4 块木板"算进材料账** |
| `skills.js:103` | ★ `await bot.craft(recipe, Math.min(craftLimit.num, num), craftingTable)` | **材料不够就少合几次，不报错** —— "调过了"不等于"做出来了" |
| `skills.js:106-108` | 自己放下的台子用完会 `collectBlock` 收回来 | 台子会回到背包，下一轮算账能直接抵掉 |

### 7f.3 `runner\workshop.mjs`：算账在前，动手在后

- `RECIPES` 15 条配方（含工作台、熔炉、箱子、火把与木/石两级的镐斧剑铲锄）、
  `NEEDS_TABLE` 11 项、`TOOL_TIERS` 四级升级链、`PICKAXE_FOR` 13 种方块 → 最低要求的镐。
- `planFor(item, count, {inv, hasTable, planksName})` 是**纯函数式的算账**：
  返回 `{ok, plan, missing, needsTable, alreadyHave}`。`plan` 是有序步骤，
  `missing` 只记**原料**（`{_log:3}` → "3 根木头"）—— 因为玩家能给的只有原料。
- `finalizeSteps()` 负责合并与排序：同一件东西合成多次并成一次；木板 → 木棍 → 工作台 →
  目标，**目标永远最后**。
- `runPlan(agent, plan, {craftOne})` **每一步做完都重新数一遍背包**。这一条是被
  `skills.js:103` 逼出来的：引擎说"做成了"而背包没变时，必须判失败并立刻收手
  （后面几步必然也缺料），不能继续往下调。

### 7f.4 `ensurePickaxe()`：真正"陪"玩家的那一步

```js
async function ensurePickaxe(agent, block, { say, onProgress }) {
    const need = PICKAXE_FOR[block] || 'wooden_pickaxe';
    const mine = bestTool(agent.bot, 'pickaxe');
    if (mine && tierRank(mine) >= tierRank(need)) return { ok: true, tool: mine };
    if (!canCraft(need)) return { ok: false, message: `挖X得有把铁镐，这个我暂时做不出来 …` };
    let r = await craftTool(agent, need, { say, onProgress });
    // 差圆石、而我们连木镐都没有 → 先做木镐去挖圆石，再回来做
    if (!r.ok && r.missing?.cobblestone) {
        const bootstrap = await craftTool(agent, 'wooden_pickaxe', { say, onProgress });
        if (bootstrap.ok) {
            await equipTool(agent, 'wooden_pickaxe');
            say(`我先做把木镐，挖${r.missing.cobblestone}块石头回来。`);
            await executeCommandFn(agent, `!collectBlocks("stone", ${r.missing.cobblestone})`);
            r = await craftTool(agent, need, { say, onProgress });
        } else if (bootstrap.missing) { r = { ok: false, missing: bootstrap.missing }; }
    }
    …
}
```

**关键设计：能自己解决就绝不开口要东西。** 只有当连木镐都做不出来（没有木头）时，
才回一句「挖石头得有把木镐，做它要 3 根木头，我手上还没有。你先给我，或者说一声"砍点木头"，我去弄。」

## 七·补六、烧炼链 + 让 bot 说人话

### 7g.1 为什么烧炼不能走引擎的命令

引擎有个 `!smeltItem` 命令，看起来正合用。**但它在成功后 500ms 会自杀。**
`vendor\mindcraft-develop\src\agent\commands\actions.js:284-291`：

```js
if (success) {
    setTimeout(() => { agent.cleanKill('Safely restarting to update inventory.'); }, 500);
}
```

也就是说每烧一次熔炉，面板上就多一条"意外退出"，`supervisor` 还要按退避策略重连一次。
而**库函数** `skills.js:142 smeltItem(bot, itemName, num)` 做完是正常返回的。

→ 结论：我们在 `runner\mcbot-gate.mjs` 里直接调库函数：
```js
async function smeltOne(agent, rawItem, times) { return skills.smeltItem(agent.bot, rawItem, times); }
```

顺带记住 `utils\mcdata.js:284` 的口径：`isSmeltable()` 只认 `raw*` / `*log` /
`misc_smeltables` —— **只能烧 `raw_iron`，不能烧 `iron_ore`**。账要算到"原铁矿"那一层。

### 7g.2 让 bot 自己把缺的东西挖回来

`craftTool()` 原来是"算账 → 缺料就开口要"。现在中间插了一步
**`fetchMissing()`**，把"缺什么"变成"自己去挖"：

```js
const MINE_FOR = { _log:'oak_log', cobblestone:'stone', coal:'coal_ore',
                   raw_iron:'iron_ore', raw_copper:'copper_ore', raw_gold:'gold_ore' };
```

每一项先递归 `ensurePickaxe()`（`depth > 2` 收手，防止"挖铁矿要石镐、做石镐要圆石、
挖圆石要木镐、做木镐要木头……"无限套娃），再 `!collectBlocks`。
**`_log → oak_log` 这一条是整个自给自足链能成立的关键** —— 没木头就先去砍树。

`ensurePickaxe()` 也顺势从"两级链"简化成递归链，并且修掉一个真 bug：
旧版 `PICKAXE_FOR[block] || 'wooden_pickaxe'` 会**逼着木头也要木镐**；
现在 `if (!need) return { ok:true, tool:null }` —— 木头/泥土/沙子空手就能采。

### 7g.4 🔴 真机暴露的 UX 缺口：玩家在读英文日志

挖铁矿那一次，聊天框里发出来的是**引擎原样的英文**：

```

Collected 11 iron_ore.
```

信息量其实很足（挖到 11 个就走不过去了），但读起来是英文 + 内部术语。
一个陪伴型 bot 不该让主人去读日志。

→ 新建 `runner\engine-speak.mjs`（纯函数，导出 `translateEngineReply` / `nameOf`）。
引擎的输出是**多行**的（`skills.js:10-12` 是 `bot.output += message + '\n'`，
`action_manager.js:158-162` 再包一层 `'Action output:\n'`），所以按行翻译、
用空格接起来 —— 一行正好对上 `skills.js` 里的一处 `log()`。实测：

```
小豆 挖点钻石 → <Xiaodou> 附近没有钻石矿。 挖到了 0 个钻石矿。
```

三条设计原则（缺一条都会变成"看起来更好"的坏事）：

1. **认不出的原样返回英文**。宁可给英文，也不要胡编一句听起来合理的话 ——
   玩家看到英文至少知道出了没预料到的事，看到编的中文反而会被误导。
2. **数字一个不改**：挖到几个、差几格、要几个，全部照抄。
3. **名字靠已有的表**：方块名查 `runner\vocab.mjs` 的词典、产物名查
   `runner\workshop.mjs` 的配方表。单测里有一条断言专门守这个：
   **词典里 37 条方块名，翻译层和意图层说法必须完全一致** ——
   两张表各写各的，迟早会出现"玩家说挖煤、bot 回 coal_ore"这种事。

### 7g.6 一个自己撞上的架构问题：改了话头，老用户收不到

`migrateConfig()` 的原则是"只增不改"：按 id 补齐缺失的内置规则。
但这条原则有个副作用 —— **加规则能送到，改规则的话头送不到**。
用户的 `config.json` 里已经有 `seek` 了，所以我们把话头从 6 条加到 9 条，
他那边还是 6 条，而界面上那条规则明明开着。

修法（`app\electron\store.mjs`）：记一份 `PREV_DEFAULT_PATTERNS`，
里面存着**上一版内置话头长什么样**；迁移时只有当用户当前的 patterns
和旧默认**一模一样**（= 没自己改过）才刷成新的。

```
旧默认话头      → ["找找","找一下","附近有没有","附近有","有没有","哪有","哪里有","哪儿有","带我去找"]
用户改过的话头  → ["我自己写的话头"]        ← 一个字都没碰
```

**用户的改动比我们的新默认值重要** —— 这条边界不划清，一次"帮你改好话头"
就会变成"把我的设置冲掉了"。

### 7h.3 改法：门禁里抢在 `commandExists()` 之前

`runner\self-report.mjs` 顶部导出唯一的一份登记表：

```js
export const LOCAL_REPORTS = { '!stats': 'stats', '!inventory': 'inventory' };
```

`runner\mcbot-gate.mjs` 的 `if (cleaned.startsWith('!'))` 分支里，在 `commandExists()` **之前**：

```js
const localReport = LOCAL_REPORTS[cleaned.split(/[\s(]/)[0]];
if (localReport) {
    stats.localReports = (stats.localReports || 0) + 1;
    emit('gate', { decision: 'PASS', via: 'command', from: username, msg: cleaned, cmd: `<本地汇报:${localReport}>`, channel });

```

### 7h.5 覆盖检查加第二段：55 条命令逐条登记

`tools\check-speak-coverage.mjs` 原来只扫 `skills.js` 的 `log(bot, …)`（143 句），
**扫不到"玩家主动敲命令"产生的文本** —— 这次就是从这个缝里漏的。现在加第二段，逐条登记：

| 归类 | 条数 | 规则 |

| `ENGINE_ONLY` | 53 | 有意交给引擎，**每条都写清为什么** |
| 两边都不在 | 0 | **报"没登记"并 `process.exit(1)`** |

还会**反向查**：`ENGINE_ONLY` 里登记了、但引擎里已经删掉的命令 → 报"过期登记"并退出 1。

几条关键的"有意不管"及理由：

- `!nearbyBlocks` / `!craftable` / `!entities` —— 这是**给模型看的清单**，玩家想问有中文话头
- `!modes` —— `self_preservation` 那种内部开关说明书，本来就不是说给玩家听的
- `!stop` / `!stfu` —— ★ **必须永远能用、零延迟**，绝不能排在限流后面
- `!smeltItem` —— ★ 在引擎里会自杀重启（`commands\actions.js:284-291`），我们只在库层调
- `!rememberHere` / `!goToRememberedPlace` —— 我们有中文的 `runner\memory.mjs`

**并且反向验证了它真会红**（本项目硬纪律）：临时把 `!nearbyBlocks` 从表里摘掉 → EXIT=1；
临时插一条 `['!noSuchCommand','假的']` → EXIT=1；还原后 EXIT=0。

### 7h.6 把"哪几套自检"变成代码里的清单 —— 然后被它自己咬了一口

以前每轮收尾都手打一段 PowerShell 把十几套命令抄一遍。**抄漏过一次
`--import ./devtools/register-electron-stub.mjs`**，`test-llm-errors` 于是报
`SyntaxError: Named export 'safeStorage' not found`，看着像代码坏了，其实只是跑法不对，白查一轮。

新建 `tools\run-all-tests.mjs`（14 套，约 90 秒）。**第一版它报了假绿**：

```

✓ headless-multibot          80ms     ← 单独跑要 33 秒、打 36 项
✓ headless-multiserver       79ms
✓ 14 套自检全绿                        ← 全是假的
```

根因是我把 stub 写成了 `['./devtools/register-electron-stub.mjs']`，拼出来是
`node <stub文件> <自检文件>` —— **少了 `--import`**，等于把 stub 当入口脚本跑，
它注册完就退了。退出码 0、输出为空、"通过"。

1. `const STUB = ['--import', './devtools/register-electron-stub.mjs'];`
2. **每套都带一个 `expect` 正则，没打出那句"跑完了"的汇总就算失败** ——

### 7h.7 又一个真 bug：自检偷偷连到了用户的线上服

`headless-multibot` 三处断言齐红（唤醒不串台那几条）。查沙箱事件文件第一行：

```json

```

**bot A 登录的是用户的真服务器，不是本机 25565。** 测试玩家在本地服喊话，
A 一条门禁事件都收不到（`A 本次：门禁 0 条（放行 0）`）—— 代码一行没错，
是**测试的位置假设过期了**：

1. `const srv = cfg.servers[0];` —— 用户后来把自己的服务器加进配置且**排在数组前面**，
   `servers[0]` 一夜之间从"本机测试服"变成了"用户的线上服"，脚本于是把**用户那台**
   的 host/port 改成了 `127.0.0.1`（改的是沙箱副本，没伤到真配置）。
2. **`botA.serverId` 从来没被重指过** —— supervisor 是按 `bot.serverId` 回配置里反查服务器的，
   光改 `srv` 变量没用。

修法三层（`devtools\sandbox-env.mjs` 新增 `isLoopbackHost()` / `pickLoopbackServer()`）：

1. **按意图挑，不按位置挑**：`pickLoopbackServer(cfg.servers)`，
   挑不到就 `fail` + 退出 1（并列出当前所有服务器）。
2. 显式绑 `botA.serverId = srv.id;`
3. ★★ **最后一道闸**：拿 `buildLaunchSpec` 出来的 spec 断言目标服务器必须是回环，
   否则直接停下 —— 无论上面哪一步写错，都出不去。

同一套修法也应用到了 `headless-multiserver.mjs` 和 `headless-main.mjs:267` 的真服务器探测
（那里的"跳过"分支匹配也从 `/拒绝了连接|连接超时/` 放宽到加上了 `域名解析|找不到|没找到`，
否则用户一断网、域名解析失败的文案匹配不上，整套自检会莫名其妙变红）。

> **挑东西要按意图挑，不能按位置挑。** 位置是别人（用户的配置）控制的，随时会变；
> 变的时候测试**不会报错，只会静默失效**。

### 7i.2 第一个坑：`.cmd` 里的中文，代码层面永远看不出来

`启动.cmd` 的实测字节：`bytes=962 非ASCII=333 LF=39 CRLF=0 BOM=false`。

cmd.exe **不认 BOM，也不按 UTF-8 读** —— 它用当前控制台代码页（中文 Windows = GBK/936）
去解码文件内容。UTF-8 的中文被按 GBK 解出来是一串乱码，而这串乱码里**包含了把换行吃掉的情况**，
于是 `rem 这是一句注释` 和它下面那行命令被**拼成了一条命令**去执行：

```
rem 启动前先把环境变量清掉，否则窗口根本不会出现。set ELECTRON_RUN_AS_NODE=
        └────────────── 被当成一整条命令 ──────────────┘
→ '竻鎺夛紝鍚﹀垯…set' 不是内部或外部命令
```

每一句中文注释都变成一条这样的报错，`electron` 那行压根没执行到。**这类 bug 不可能靠
读代码发现** —— 文件在编辑器里长得完全正常。

**修法（不是"把编码改成 GBK"）**：`.cmd` 只留**纯 ASCII**，中文全部搬进 `.ps1`。
PowerShell 认 BOM，所以 `.ps1` 用 **UTF-8 带 BOM + CRLF** 就能正确显示中文。

| 文件 | 内容 | 字节要求 |
|---|---|---|
| `启动.cmd` / `预览界面.cmd` | ~15 行纯 ASCII，只负责 `powershell -File tools\launch-gui.ps1 %*` | 零个 >127 字节、CRLF、无 BOM |
| `tools\launch-gui.ps1` | 所有中文提示、体检、退出码诊断 | UTF-8 **BOM**、CRLF |

新增 `tools\check-launchers.mjs`（`--fix` 只改字节不改内容）：扫 `.`/`tools`/`devtools`/`docs`/`app`/`runner`
下的 `.cmd/.bat/.ps1`（**刻意排除 `runtime/`、`vendor/`** —— Node 发行版自带一堆 `.cmd`，不归我们管）。
反向验证过它真能抓：修之前报 `启动.cmd 有 22 处 LF`、`预览界面.cmd 有 6 个非 ASCII 字节 + 12 处 LF`，
EXIT=1。★ 它连**注释里的中文**都不放过 —— 我在 `预览界面.cmd` 里写了句「见 启动.cmd」，照样被抓出来。

### 7i.3 第二个坑：PowerShell 用 `&` 调 GUI 子系统程序，**根本不等它**

第一版 `launch-gui.ps1` 写的是最自然的写法：

```powershell
& $electron $appDir          # ← 错
Write-Host "退出码 $LASTEXITCODE"
```

`electron.exe` 是 **GUI 子系统**程序（PE 头里没有控制台），PowerShell 用 `&` 调它**立刻返回**、
也**不设置 `$LASTEXITCODE`**。后果：用户双击 → 黑窗口一闪就关 → 看着像什么都没发生，
而下面那整段"退出原因诊断"代码永远跑不到。**这正是用户看到的现象。**

改成 .NET API，显式等它：

```powershell
$psi = New-Object System.Diagnostics.ProcessStartInfo
$psi.FileName        = $electron
$psi.Arguments       = '"' + $appDir + '"'
$psi.WorkingDirectory = $root
$psi.UseShellExecute = $false     # 继承当前控制台与环境变量
$proc = [System.Diagnostics.Process]::Start($psi)
$proc.WaitForExit()
$code = $proc.ExitCode
```

不用 `Start-Process` 的理由：它的 `-ArgumentList` 对含空格路径的加引号规则很绕，
而"路径里有空格就启动失败"正是这类怪问题的经典来源。

退出码分两支：`$unsigned = $code -band 0xFFFFFFFF`，`>= 0x80000000` 就说明
**Electron 自己都没起来**（跟服务器、API Key 都无关），打印十六进制码 + 四条方向
（远程桌面/虚拟机、杀毒软件、VC++ 运行库、Electron 下载不完整）；否则才列
"MC 账号被顶号 / 服务器地址 / API Key"。

**验证证据**：PS 5.1.26100.9444 用官方 parser 解析 `launch-gui.ps1` → `tokens=870, 0 errors`；
用**码点比较**（命令行里不传中文，避免编码干扰）证明 PS 5.1 确实把中文读对了；
`cmd /c "启动.cmd -NoPause"` 中文输出完全正常，真的拉起了 Electron 并等到退出码
**0x80000003 / 391ms** —— 也就是**本开发环境里 Electron 仍然起不来**（没有交互式桌面），
但"cmd → powershell → 中文 → 拉起 electron → 诊断退出码"这条链子每一环都通了。

### 7i.4 第三个坑（最隐蔽）：对陌生人**静默拒绝**

修好窗口之后还有第二个"看起来像坏了"的现象，而且它比第一个更糟 —— **它不报错**。

`runner\mcbot-gate.mjs` 里：

```js
if (!owners.some((o) => lower(o) === lower(username))) {
    reject('rejectedNotOwner', username, message);
    return;                       // ← 一句话都不回
}
```

而出厂配置 `app\electron\store.mjs:157` 是 `owners: ['Steve']`。
注意它是**非空**的 —— 所以 `validateConfig` 的"必须指定至少一个主人"不响，
界面上的"没有配 owner"警告也不响。用户用自己的 ID 进游戏喊一句，得到的是**永久沉默**：
没有回复、没有报错、界面上没有任何异常。他只会得出一个结论：**这东西是坏的。**

**三处修法（每一处都缺一不可）：**

1. **`ownersConfigured` 显式标记**（`store.mjs` → `launcher.mjs` → `engine-launcher.mjs` → `mcbot-gate.mjs` 一路透传）。
   三档推断，顺序不能反：
   ```js
   ownersConfigured: typeof b.ownersConfigured === 'boolean'
       ? b.ownersConfigured                                  // 显式说了算
       : (owners.length > 0 && !isFactoryOwners(owners)),    // 老配置升级：名单≠出厂值就算配过
   ```
   两个"没配过"的情形：出厂 `['Steve']`、或者刚新建的 `[]`。
2. **GUI 首跑卡**：机器人页顶部一张卡，直接让你把游戏 ID 填进去，一键写到**所有**未认领的 bot 上。
   文案里明说"名单外的人说话它一句话都不会回，看起来就像坏了" —— 把沉默解释清楚。
3. **游戏内一次性提示**：未认领时，名单外的人说话会得到一句
   「我还没被认领呢。打开应用，在「机器人」页把「主人」改成你的游戏 ID，我才听得见你说话。」
   三条约束：**只在明确 `ownersConfigured === false` 时说**、**每个玩家每会话只说一次**、
   **私聊永远算而公屏必须带唤醒称谓**（否则就变成对着全服广播"这个号没主人"）。

顺带把「机器人」页从"只读展示"补成了**真的能改**：MC 账号名 / 中文名 / 唤醒称谓 / 主人 /
服务器 / 大模型 / 人格 / 限流 / 每日 token 预算，加「新建机器人」「删除这台机器人」。
在此之前 **GUI 里根本没有编辑 bot 的地方**，一切都只能手改 `runtime\config.json`。

### 7i.5 为这条链路写单测，第一轮就抓出两个真 bug

这条链路的失败模式很讨厌：**任何一段丢字段，现象都是"回到永久沉默"，而且不报任何错。**
所以给它写了 `devtools\test-firstrun.mjs`（32 项，不起引擎，110ms）。第一轮跑出 5 项失败：

1. `isFactoryOwners` 拿**未小写化**的 `['Steve']` 去比已经 `toLowerCase()` 的名单 ——
   `'steve' === 'Steve'` 恒为 false → **出厂名单永远判不出来 → 首跑提示永远不出现**，无任何报错。
   修：预生成 `FACTORY_OWNERS_LC` 再比。
2. `ownersConfigured: b.ownersConfigured === true || (...)` —— **显式 `false` 被无视**
   （上面那个三档写法就是这时候定下来的）。

端到端证据写在 `devtools\headless-multibot.mjs` 新增的 **§4.5**：另起一个 `username:'Alex'`
的假玩家进服喊话，断言 ①A 被拦且**恰好回一句提示**、②**Alex 那个客户端确实收到了那句话**
（不是只写进我们自己的日志）、③再说第二句不重复提示、④私聊也不重复、
⑤喊**已配置**的 B 时一句提示都没有、⑥公屏不带称谓的闲聊不提示。51 项全绿。

### 7i.6 顺手修掉的一个真 UX 缺陷：保存会把正在编辑的卡片折叠掉

界面自检（`render-headless.mjs` §5）点开卡片后断言"编辑区在"，结果三条失败。
一开始以为是 `renderEdit()` 抛异常，dump 出来的现象很怪：**按钮已经写着「收起详情 ▴」、
里面却是空的**。真相是：

`app\renderer\app.js` 的 `saveConfig()` **成功之后**会调 `remountView()`
（注释原文「直接重挂：清掉视图内部状态，避免它抱着旧的对象引用」），
而 `bots.js` 的视图状态原本是 `render()` 内部的局部变量 —— **一次重挂就归零**。
所以真实体验是：点开卡片 → 改字段 → 按「保存配置」→ 编辑区**当场自己合上**，
看起来像改动被丢了。（而第一版测试是"点早了"，点到的是马上要被丢掉的那棵 DOM，
所以现象时有时无 —— 竞态。）

修法：把"哪几张卡是展开的"提到**模块级** `const openCards = new Set();`。
顺带好处：切到别的页再回来，展开的卡片还开着。
★ 踩坑：改状态持有方式时只改了声明、漏了 5 处引用，报出来的错是
`TypeError: state.detailOpen is not iterable` —— **错误信息指向的地方跟改动的地方完全无关**。

同时收紧了两条**假阳性断言**：原来拿整页 `innerHTML` 去 `includes('主人')`，
而 toast 文案里也有「主人」「小豆」，于是两条根本不存在的字段"通过"了。
现在只查 `querySelector('.edit-grid').textContent` 这个小范围，并新增一条回归守卫：
点「保存配置」→ 等 700ms → 断言编辑区**仍然存在**。

### 7i.7 修完之后，另一套自检红了 —— 但它红得对

改完配置（把 `bot-axiao.owners` 从 `['Steve']` 改成用户给自己的那个游戏 ID）之后重跑全量自检，
`headless-multiserver` 报了 2 项失败：

```
✗ B 放行了却没有任何大模型调用 —— 链路断了
```

乍看像是我把门禁改坏了。去读沙箱里的事件流，真相一秒钟就出来了：

```json
{"type":"gate","decision":"BLOCK","reason":"rejectedNotOwner","from":"Steve","msg":"阿霄 你好呀"}
```

**门禁按新名单把测试玩家 Steve 判成了陌生人。** 而这个脚本第 141-151 行是这样写的：

```js
let botB = cfg.bots.find((b) => b.id === B_ID);
if (!botB) {
  botB = store.makeBot(...);
  Object.assign(botB, { ..., wakeNames: ['阿霄', ...], owners: ['Steve'] });
  cfg.bots.push(botB);
}
```

它从**用户的真配置**（沙箱副本）里找 `bot-axiao` —— 找到就**整个跳过**那段赋值。
也就是说：**这套"多服务器并行"自检，一直在偷偷依赖"用户那台 bot 的主人正好叫 Steve"**
（出厂默认值凑巧等于测试玩家的名字）。用户的名单一改，它测的就不是服务器隔离了，
而是"我的名单改对了没有"。修法是把被断言的性质**无条件钉死**（`wakeNames` / `owners` /
`ownersConfigured` 全部由测试自己设），修完 31 项全绿。

这跟 §7h.7 那个 `servers[0]` 是同一种病：**测试没有自己摆好前提，而是碰巧站在用户的数据上。**
区别是上次错在"按位置挑"，这次错在"按用户数据挑"。共同教训：
**凡是断言依赖的性质，都要由测试自己建立；改完用户配置必须重跑一遍全量自检。**

### 7i.8 更严重的一次：那道"必须连本机"的闸，建在了错的地方

7i.7 那一节修完，我顺手把 `bot-axiao` 也指到了用户的服务器（否则他点「启动全部」的时候，
阿霄会因为连不上 `127.0.0.1:25565` 而报错 —— 那是本地测试用的演示条目，他机器上没这个服）。
然后 `headless-multibot` 又红了，4 项：

```
✗ 没看到两个 bot 各自记下 rejectedNoWakeName
✗ B 没有记下 rejectedNoWakeName，说明它可能压根没收到公屏
✗ 叫"阿霄"但 B 没放行
✗ 陌生人喊 B 没记下 rejectedNotOwner
```

去读沙箱里 B 的启动日志，第一行就是：

```
[MCBOT-LAUNCHER] server     : <你的服务器地址>:<端口> (1.21.1, offline)
[MCBOT-EV] LOG 启动配置：<你的服务器地址>:<端口> · mcbot-spike-model · 人格 builder
Axiao spawned.
```

**这套自检刚刚把 bot「阿霄」登进了用户的线上服务器。**（它现在 `owners: ['Steve']`，
所以用户本人说话会被当陌生人拒掉；跑完已正常停止，没有残留进程。但这是必须说清楚的事。）

根因有两层：

1. **B 的服务器绑定没钉死。** 脚本从用户的真配置里找 `bot-axiao`，找到就跳过那段赋值 ——
   于是 B 挂哪台服**完全由用户配置决定**。A 早在上一轮就修过（`botA.serverId = srv.id`），
   B 漏了。
2. 🔴 **那道"必须连本机"的闸建错了地方。** 它检查的是
   `buildLaunchSpec(botB, srv, cfg.llm.profiles[0]).spec` —— **`srv` 是我们显式传进去的**，
   算出来的 spec 当然是 `127.0.0.1`，属于自问自答。
   而 `supervisor.start(botId)` 起进程时走的是**另一条链**：
   `bot.serverId` → 从**已保存的配置**里反查 `servers[]` → `host`。
   **闸门和被测对象走的不是同一条链，等于没有闸门。**
   （注释里甚至写着"以后配置再怎么排、字段再怎么加，只要 spec 里的地址不是本机，这里就当场拦下"
   —— 它拦的是自己刚刚构造出来的那个对象。）

**修法**：闸门挪到 `saveConfigRaw(cfg)` **之后**，读回**已保存的配置**，
对每个即将启动的 bot 走一遍 `serverId → servers[] → host`，不是本机就当场停：

```js
const saved = store.loadConfigRaw();
const srvById = new Map(saved.servers.map((s) => [s.id, s]));
for (const id of [botA.id, botB.id]) {
    const sb = saved.bots.find((b) => b.id === id);
    const s = sb ? srvById.get(sb.serverId) : null;
    if (!(s && isLoopbackHost(s.host))) { /* 报错并 process.exit(1) */ }
}
```

★ 并且给它配了**反向验证开关** `MCBOT_VERIFY_GATE=1`：故意把 B 指到 `192.0.2.1`
（TEST-NET-1，保留地址，永远不会路由到真实主机）。实测 **427ms、退出码 1**，
在起任何进程之前就拦下了：

```
✗ ★ 自检会连到 bot-axiao → 192.0.2.1:25565 —— 不是本机，拒绝继续（这套自检只连本机）
```

**教训有两层，第二层更贵：**
- 测试没有自己摆好前提，而是碰巧站在用户的数据上（同 §7h.7 的 `servers[0]`，
  那次错在"按位置挑"，这次错在"按用户数据挑"）。
- **闸门必须建在"被测对象真正走的那条链"上。** 一个检查了错对象的断言，
  比没有断言更危险 —— 它会让你以为这件事已经被守住了。
  凡是写"最后一道闸"，都要顺手问一句：**这道闸检查的东西，和实际发生的那件事，
  是同一条链吗？** 并且**必须能反向验证它真的会响**。

### 7i.9 「密钥我填过了」—— 一次差点漏过去的假密钥

修完上面那些，我去核对用户的真实配置，想看看到底缺什么。结果是这样：

```
bot-xiaodou | Xiaodou(小豆) | owners=["（你的游戏 ID，已脱敏）"] | configured=true | enabled=false | srv=<你的服务器地址>:<端口> …
secret deepseek: 长度=16 掩码=sk-…fake
```

`sk-…fake` —— 用户不可能填出这种密钥。把 base64 解出来是 **`sk-multibot-fake`**，
也就是 `devtools/headless-multibot.mjs` 里写死的那把测试密钥。

**真相是：早期还没做沙箱的自检，把它的测试密钥写进了用户的 `runtime\secrets.json`。**
（`enc: false` 也印证了这一点 —— 真实 Electron 下 DPAPI 一定可用，写出来的是 `enc: true`；
只有跑在 electron stub 下的脚本才会走明文分支。）它一直躺在那儿，
界面照着它显示「已保存（sk-…fake）」，**和真密钥长得一模一样**。
用户会得到的最坏结论是："密钥我明明填过了，怎么还是不通"。

**修法分两步：**
1. 界面上把"有密钥"再拆成两种：`keyIsPlaceholder` 为真时，状态写
   「已保存（sk-…fake）—— 但这看着像测试用的假密钥」（`.key-state.warn`，红字），
   下面再补一块说明："它跑不通真实的大模型接口，请把你的 API Key 粘上来覆盖掉它。"
   判定在 `store.looksLikePlaceholderKey()`：只认 `sk-test-` / `sk-headless-` /
   `sk-multibot-` / 中间夹 `test|fake|dummy` / `changeme` 这类**明确是假的**形态 ——
   真密钥被误判成假的，比漏判更糟（用户会去反复重填一把本来好好的 Key）。
2. `tools\clean-fake-keys.mjs` 把那条记录删掉。它**只删判定为假的**，
   形态奇怪但可能是真的密钥一律不动 —— 删除不可逆，宁可留着一条碍眼的记录。
   实跑输出：`- deepseek：sk-…fake 判定为假密钥（早期自检留下的），删除` →
   `runtime\secrets.json` 变成 `{}`。现在模型页会诚实地写「还没保存密钥」。

**顺带记下一个把我也骗了半天的坑**：`secrets.json` 里存的**不是字符串**，
而是 `{ enc: bool, v: base64 }` 这个**对象**。我第一版探针写的是 `String(rec).length`，
于是打印出 `"[object Object]"`（长度 15）—— 我差点又一次得出"密钥没保存上"的错结论。
正确的判据只有一个：**能不能把它取回来**（`store.getSecret(id)` 有值才算有）。
看密钥状态要用 `store.secretStates()`，别自己去解那个文件。

## 七·补九、`0x80000003`：一次"看起来像环境坏了"的真 bug

### 7j.1 用户报障原文（要点）

你先把发布的事往后放了（原文大意：「发布到 github 的事明天再说」，当前先解决启动窗口），
然后发来同一类现象：**双击 `启动.cmd` 之后黑窗口里已经能正常显示中文了**（说明 §7i 修的那条
链子确实通了），紧接着出现的是启动器自己打的那句

```
Electron 自己没能启动起来（退出码 0x80000003）。
```

—— 注意这句话的含义：**配置、密钥、服务器地址、我们的代码，一个都还没轮到被检查**。
它说的是"`electron.exe` 这个进程还没跑到能读我们代码的地方就死了"。

### 7j.2 先排掉两个最省事的怀疑

| 怀疑 | 取证 | 结论 |
|---|---|---|
| 系统太老 / 不受支持 | `Get-CimInstance Win32_OperatingSystem` → `Microsoft Windows 11 家庭版 中文版`，`Version 10.0.26200`，`BuildNumber 26200`，64 位 | **排除**。Electron 44 支持 Win10+，26200 是新系统 |
| Electron 没下全 | `app\node_modules\electron\dist\` 逐个点：`electron.exe` 234.34 MB、`icudtl.dat` 10.37 MB、`resources.pak` 11.86 MB、`LICENSES.chromium.html` 19.52 MB、`d3dcompiler_47.dll` / `dxcompiler.dll` / `dxil.dll` / `ffmpeg.dll` / `vk_swiftshader.dll` / `vulkan-1.dll` 全在、`locales\` 55 个文件、`resources\` 1 个文件 | **排除**。文件是齐的 |

（`libEGL.dll` / `libGLESv2.dll` 不在清单里 —— 新版 Electron 已经不带这两个，不是缺文件。）

### 7j.3 关键取证：**`electron.exe --version` 自己就崩**

```
electron.exe --version                          → 退出码 0x80000003，stdout/stderr 全空
electron.exe --version --enable-logging=stderr --v=1 → 同样全空
```

★ 这一步的意义很大：**连 `--version` 都崩、而且一点日志都吐不出来**，说明它死在 Chromium
打印任何东西之前，和我们的应用代码、`runtime\config.json`、密钥、服务器地址**全部无关**。
也正因为没有输出，`0x80000003` 这个数字本身就成了唯一的线索。

`0x80000003` = `STATUS_BREAKPOINT`，在 Chromium 里由 `IMMEDIATE_CRASH()`
（底层是 `__debugbreak()`）触发 —— **它表达的是"某个 CHECK 断言没通过"，不是"显卡不支持"
这类软故障**。所以方向不是"换个渲染方式"，而是"哪一层初始化过不去"。

### 7j.4 用排除法定到"主进程沙箱"

| 试的开关 | 结果 | 说明 |
|---|---|---|
| `--disable-gpu` | 仍然 `0x80000003` | **不是** GPU 子系统 |
| `--disable-gpu-sandbox` | 仍然 `0x80000003` | **不是** GPU 沙箱 |
| `--in-process-gpu` | 仍然 `0x80000003` | 同上 |
| **`--no-sandbox`** | **正常打印 `v44.5.1`，退出码 0** | ✅ 就是它 |
| `electron.exe "D:\mc_company_bot\app" --no-sandbox` | 窗口真的出来了 | 见 7j.7 |

三个和 GPU 有关的开关全无效、只有"关掉沙箱"有效 —— 结论只能是**主进程那个沙箱**
（`RendererSandbox` 之外的那个）在这台机器上初始化失败。

### 7j.5 这台机器为什么特殊

- 登录用户 `laptop-abps9bs3\exus1ai`，**不是管理员**；
- **腾讯电脑管家在跑**（`QQPCRTP` 进程；`SecurityCenter2` 报的是"腾讯电脑管家系统防护"）；
- Windows Defender：实时防护**开**、篡改防护**开**、智能应用控制 `Off`、ASR 规则 0 条、
  受控文件夹访问 `Off`；
- **「内存完整性」（HVCI）`Enabled = 1`**。

安全软件拦截 + HVCI 是 Chromium 沙箱最典型的两类对手（沙箱要装内核回调、要用到
代码完整性不喜欢的那些手段）。**这两样都在你机器上、而且都不该由程序偷偷去改**，
所以正确的做法不是"教你关掉杀软"，而是**代码里让路**。

### 7j.6 修法：先按正常方式起，崩了再降一级（而不是直接关沙箱）

`tools\launch-gui.ps1` 的启动段从一个 `& $electron $appDir` 变成了**最多两次尝试的循环**：

- 常量 `$SANDBOX_CRASH = 0x80000003`；`$attempt = 0` 时**不加任何参数**（保留沙箱），
  `$attempt = 1` 时才加 `--no-sandbox`。
- 用 `$proc.WaitForExit(8000)` 探测：**8 秒内就退出、且退出码正好是 `0x80000003`** →
  打印一段人话（沙箱起不来、正在自动换一种方式、以及"想彻底修好该怎么做"），
  然后用 `--no-sandbox` **重新起一次**；8 秒还活着就 `WaitForExit()` 老老实实等它结束。
- 为什么是 8 秒：实测这个崩溃发生在**1 秒内**，而正常启动到窗口出现要几秒；
  8 秒足够把"崩了"和"起来了"分开，又不会让用户白等。
- ★ 为什么不用 `& $electron` 或 `Start-Process -Wait`：**PowerShell 调用 GUI 子系统程序时
  不等它**，拿不到退出码，"崩没崩"就无从判断（这个坑 §7i.3 已经踩过一次，这次是同一个坑的
  第二副面孔）。
- ★ **第一次仍然保留沙箱**：只有真崩了才降级。否则就是"因为一台机器的毛病，
  让所有用户的浏览器内核都裸奔"。

失败的提示也按"降级了没有"分开：降级后仍然崩 → 让用户把窗口内容截图发我；
没降级就崩 → 列出真实的三条原因（安全软件拦沙箱 / 「内存完整性」开着 / 远程桌面·虚拟机）。

`-Check`（只看病不开窗口）也一起升级了：它现在**真的跑一次** `electron.exe --version`
和 `--version --no-sandbox`，输出像这样

```
带沙箱启动 : 起不来，退出码 0x80000003
关掉沙箱启动 : OK（v44.5.1）
```

—— 光用 `Test-Path` 查"文件在不在"是**查不出"文件在、一跑就崩"**的。

### 7j.8 让这类回归以后在自检里报红

1. **字节**（原有）：`.cmd` 纯 ASCII + CRLF、`.ps1` 带 UTF-8 BOM + CRLF；
2. **内容不变量**（新）：启动器必须还在"等进程结束 / 认得 `0x80000003` / 崩了自动加
   `--no-sandbox` 重试 / `-Check` 真的跑一次 Electron"这条路上，共 6 条；
   外加一条「`启动.cmd` 真的会走到 `launch-gui.ps1`」；
3. **沙箱体检**（新）：用真 `electron.exe` 探一次，**只报告不判失败** ——
   这是机器环境，不是我们的代码，不能因为它红就把 17 套自检拖红。

写这一节时又红了两次，两次都值得记：

- ★ **断言的第一版把注释当成代码**：那条"不许退回 `& $electron` 的写法"直接对整个文件跑正则，
  于是启动器注释里那句「**绝对不能**写成 `& $electron $appDir`」把自己告了（6 条里红 1 条）。
  修法：先 `stripPsComments()` 剥掉整行/行尾 `#` 与 `<# #>` 块，**所有断言都跑在剥过注释的
  代码上**。断言的对象是代码，不是文本。
- ★ **体检被自检自己注入的环境变量污染成假绿**：这套自检是用
  `--import register-electron-stub.mjs` 跑的，子进程会继承 `NODE_OPTIONS` ——
  于是"真的 `electron.exe`"加载了我们的 stub，`--version` 打印出**stub 的假版本号
  `v24.21.0`、退出码 0**，体检报告"沙箱正常"。真相是这台机器沙箱根本起不来。
  修法：spawn 之前 `delete probeEnv.NODE_OPTIONS; delete probeEnv.ELECTRON_RUN_AS_NODE;`。
  **凡是要探测"没有我们的东西在场时会怎样"，都要先把我们注入的环境摘干净。**

### 7j.9 怎么复现

```powershell

& powershell -NoProfile -ExecutionPolicy Bypass -File tools\launch-gui.ps1 -Check

# 2) 直接问 Electron 自己（最省事的取证，一眼看出是不是它的锅）
```

### 7j.10 诚实的边界

- 我是**用命令行参数**把窗口开出来的（`--no-sandbox`），**不是双击 `启动.cmd`**。
  "双击也能开"这件事仍然请你确认一次 —— 两条路的差别只在于启动器会不会自动降级，
  而自动降级那段逻辑我已经单独跑过、日志里能看到它确实降了级。

## 七·补十、"密钥我填好了"的第三次核对 + 自检差点冤枉产品的那条断言

这一节记录收尾时并行的两条线：一条是"用户说他填好 Key 了，到底算不算数"，
另一条是上一节留下的最后一条红色断言（`✗ A 的提示句数不对：期望 2 实得 1`）。
两条线都结清了，也都各自留下了一条值得写下来的教训。

### 7k.1 起因

用户在 22:50 左右说「已经确认保存了deepseek的api，请继续你的收尾工作」。
上一节 §7i.9 才刚吃过一次"假密钥"的亏（用户以为填过了，其实文件里是自检写进去的 `sk-multibot-fake`），
所以这次不靠界面截图、也不靠"文件里有这条记录"下结论，直接查文件 + 真调一次。

### 7k.2 第一版判据是错的（假阴性）

`runtime\secrets.json` 是 140 字节、mtime `2026/10/5 22:50:13`，内容是
`deepseek => { enc: true, v: "…（88 字符 base64，前缀 v10）" }` —— **记录确实在，而且是加密的**。

但我第一次是在 electron stub（自检用的假 Electron）里跑探针的，看到的是：

```
"deepseek": { "present": false, "hint": "", "fake": false }
```

**这是探针的假阴性，不是"用户没填"**：密文是 DPAPI 加密的，只有真 Electron 的 `safeStorage`
解得开，stub 里 `getSecret()` 必然返回 null。判据只能是"在真 Electron 里取不取得到值"。

### 7k.3 为了拿到真判据，连撞四堵墙

写一个"最小 Electron 探针"这件事本身花了 6 轮，每一堵墙都值得记：

1. **`0xC0000005`（访问违例）**：脚本刚开始执行就崩，`app.whenReady()` 不触发、**没有任何错误输出**。
   看着像"这台机器根本跑不了 Electron"。真相是 **Electron 默认把 `userData` 放在 `%APPDATA%` 下，
   而本执行环境的文件沙箱不让写那里**；真应用 `app\electron\main.mjs:35-37` 早就把它收进
   `runtime\electron-userdata` 了，所以真应用一直好好的 —— **差别就是那一行 `app.setPath('userData', …)`**。
2. **换对了目录，还是解不开**：`safeStorage` 的解密材料**跟着 `userData` 走**。
   探针必须和真应用共用同一个 `runtime\electron-userdata`，否则照样 `hasKey=false`，
   又伪装成一次"用户没保存"。
3. **stdout 是 0 字节**：Windows 上 `electron.exe` 是 GUI 子系统程序，`*> log`、
   `Start-Process -RedirectStandardOutput`、cmd 重定向**全都拿不到输出**。探针改成把结果写文件。
   顺带发现 `cmd /c "… & echo EXIT=%ERRORLEVEL%"` 里的 `%ERRORLEVEL%` 是**解析期展开**的，
   打出来永远是旧值 —— 要拿退出码就用 `System.Diagnostics.Process` + `WaitForExit()`。
4. **死路一条（记下来免得再试）**：试过绕开 Electron，直接用 PowerShell 的
   `ProtectedData.Unprotect` 解那段密文（`v10` 前缀是 safeStorage 的版本标记，后面才是 DPAPI 数据），
   CurrentUser / LocalMachine × 有无熵四种组合**全是 `The data is invalid`**。这条路走不通。

工具最后留在 `tools\keyprobe\`（一个最小 Electron 应用壳 + `probe.mjs`），
跑法：`app\node_modules\electron\dist\electron.exe tools\keyprobe --no-sandbox`，
结果写在 `tools\keyprobe\key-verify-report.txt`；退出码 0=能用 / 2=解不开 / 3=接口报错。

### 7k.4 ✅ 结论：这把 Key 是真的，而且真的能用

```
deepseek  DeepSeek  hasKey=true  fake=false  hint=sk-…4874
解出来了：长度=35，形态=sk-…4874
看起来像假密钥吗：不是
UI 里会不会漏明文：不会（安全）
HTTP 200（187ms）
回复："好"
用量：{"prompt_tokens":9,"completion_tokens":1,"total_tokens":10,"prompt_cache_hit_tokens":0}
```

- **不是占位符**（长度 35、`sk-` 开头、`looksLikePlaceholderKey()` 判否）。
- **真的调通了**：`POST https://api.deepseek.com/v1/chat/completions`、`max_tokens:1`，187ms 返回。
  这一调顺手把成本模型的基准数字校准了：一次最小请求 `prompt=9 / completion=1`，
  且 **`prompt_cache_hit_tokens` 接口确实会返回**（缓存命中可以直接从 usage 里读，不用估）。
- **安全不变量仍然成立**：`loadConfigForUi()` 的整个对象序列化后搜不到 `sk-` 明文
  （界面拿到的只有 `sk-…4874` 这种掩码）。

### 7k.5 另一条线：那条 `✗ A 的提示句数不对` 的真因不是产品

`headless-multibot` 里的断言数的是"第三方客户端 Steve 收到了几句「我还没被认领」"。
门禁日志显示提示确实发了两次（两处 `BLOCK reason=rejectedSelf from=Xiaodou msg="我还没被认领呢。…"`），
而 Steve 只收到一句 —— 差的那一句，是**他在收到之前就被服务器踢下线了**：

```
[22:41:53] Steve joined the game
[22:41:54] Steve lost connection: Invalid move player packet received
```

`testserver\logs\latest.log` 里 `lost connection` 的原因统计：
`Disconnected` 237 次、`You logged in from another location` 2 次、
**`Invalid move player packet received` 11 次**（19:31 到 22:42 之间，测试玩家和我们的 bot 都被踢过）。

**断言数出"少一句"是对的，错的是它把"我的测试玩家掉线"记成了产品缺陷。**
另一次"8 个问题"的运行也是同一个原因：那次门禁事件里**完全没有 Steve 的任何消息**
（`Steve 最近看到的 6 条：（一条都没有）`），5 条断言跟着一起错位。

### 7k.6 修法：让自检能分清"我的测试玩家掉线"和"产品没反应"

全部在 `devtools\headless-multibot.mjs`：

- `makeTestPlayer(username)`：统一创建测试玩家，`bot.on('end')` 且非主动关闭时 **800ms 后自动重连**；
  `saw[]` 是**跨重连共享的同一个数组**（观察窗口不能因为重连就清零）；
  `bot.on('kicked')` 把原因记进 `st.kicks[]` 并打印 `! 测试玩家 X 被服务器踢了：…`。
- `say(client, text, {gapMs, reconnectMs})`：**先等 `st.spawned` 再发**；等不到就
  `st.sendFailed = true` 并明说「这句话没发出去」，**绝不对着死客户端 `chat()`** ——
  那等于石沉大海，然后被断言读成"产品没反应"。
- `kickNote(st)`：每条断言失败时贴一句「注意：测试玩家 X 期间被服务器踢过 N 次：<最后一次原因>」，
  已挂到 7 个失败分支上。
- 收尾的 `player.quit()` / `stranger.quit()` 换成 `steve.close()` / `alex.close()`：
  `quit()` 也会触发 `end` → 自动重连，日志里看着像测试自己抽风。

改完之后：单套连跑两次全绿（55 项），**完整 17 套一次全绿**（见 §九 第 10 条：此前那次单红没能复现，
所以这条算"有嫌疑根因、有观测手段"，不算"修好了"）。顺带修掉了运行器的一个真缺陷 ——
它只在 `stderr` 里找红色断言行，而 `headless-multibot` 把进度写在 `stdout`，
于是"红了却不知道红在哪"。现在两边一起找，报告里会直接打出红掉的原文。

### 7k.7 诚实的边界

- 被踢这件事**我只在本地测试服上见到了**（`Invalid move player packet received` 是原版服务端对
  客户端移动包不认可的报错）。**不能据此说你那台线上服也会踢** ——
  但"客户端必须能自动重连、断言必须把掉线和产品故障分开"这两条无论在哪台服上都成立。
- `tools\keyprobe\` 是**取证工具，不是产品的一部分**：它需要真 Electron、需要网络、会真的花掉
  一次最小请求的钱（这次是 10 token）。它**不进 17 套自检**，也不会在用户机器上自动跑。
- 密钥能调通 ≠ 每一条真机对话都成功。它只证明"钥匙是真的、门是开着的"，
  剩下的仍然要靠真机上喊它一声。

## 七·补十一、我自己毁掉了 `tools\bootstrap.mjs`，而报障信息指着别的方向

这一节记的是**一次自作自受的事故**，以及它换来的三道防线。写它的理由很直接：
用户双击启动器时看到的那句话（「依赖没补齐」）和真正的原因（**项目文件被我改坏了**）
完全是两件事 —— 如果他按那句话去查网络，能查一整晚。

### 7l.1 用户看到的原文

```

第 1 步 · 下载 Node 运行时（引擎要求 Node 22）
  Node 运行时已经就位：D:\mc_company_bot\runtime\node-v22.23.3-win-x64\node.exe（v22.23.3）
第 2 步 · 下载引擎依赖和界面运行时（约 430 MB，这一步最慢）
file:///D:/mc_company_bot/tools/bootstrap.mjs:36
  'mineflayer-pathfinder': '2.4.5',
                         ^

依赖没补齐（上面是它们自己报的原因）。
```

`第 1 步` 通过、`第 2 步` 连脚本都没加载起来 —— 报错在**第 36 行**，
而那一行在文件里本来是一句完全正常的常量。这就是"文件本身坏了"的典型形状。

### 7l.2 真相：我用 PowerShell 的文本往返改文件，把中文和换行一起毁了

我在做一条断言的**负数验证**（把 `physicsTick` 故意改成 `physicTick`，看检查抓不抓得住），
用的是这个环境里最顺手的那套写法：

```powershell
$t = Get-Content tools\bootstrap.mjs -Raw
$t = $t -replace 'physicsTick', 'physicTick'
Set-Content tools\bootstrap.mjs -Value $t -Encoding utf8
```

这套写法在这个环境里是**破坏性的**，原因有两层，缺一不可：

1. 这里的 `pwsh` 实际是 **Windows PowerShell 5.1**：`Set-Content -Encoding utf8` 会**加 BOM**；
2. `Get-Content` 读**无 BOM 的 UTF-8** 时按 **GBK(936)** 解码。

于是 `Get-Content` 出来的字符串**在一开始就是错的**。更狠的是它的错法：
一串 UTF-8 中文被 GBK 解错后，**落在行尾的多字节字符会留下一个悬空引导字节，
把紧随其后的 `0x0A` 当成 GBK 的尾字节吃掉** —— 换行被吞、多行并成一行，
连字符串的收尾单引号都能消失。实测结果：

| | 事故前 | 事故后 |
|---|---|---|
| 行数 | 488 | **449** |
| `node --check` | exit 0 | **SyntaxError: Unexpected token ':'** |
| 中文 | 正常 | `鈥斺€?` 之类 |

**不可逆**：没有任何"再存一次"能救回来（错的是解码，不是编码）。

### 7l.3 怎么救回来的（这套流程可以复用）

1. `decompress({ blockId: 'b137', full: true, toFile: 'runtime\tmp\b137-full.txt' })`
   —— 当初用 `write` 工具写这个文件时的**原始参数**还在压缩前原文里，
   是一段完整的 `{"content":"#!/usr/bin/env node\n…","file_path":"…"}`。
2. 写了个抽取脚本（`runtime\tmp\extract-bs.mjs`）：定位 `"content":"#!/usr/bin/env node`，
   从那里往前找 `{`，做一次**字符串感知的括号配对扫描**，再 `JSON.parse`，
   顺手自检（5 条补丁证据串、`ENGINE_PINS`、`PATCH_EVIDENCE`、`printNextSteps` 都在；
   再扫一遍 `鈥/锛/銆/鏂/涓` 这些乱码特征字）。
3. **交叉核对**（`runtime\tmp\crosscheck-bs.mjs`）：把坏文件里"纯 ASCII 且长度 > 12"的行
   逐条到恢复版里找 —— **0 条丢失**；`function|const|let` 标识符 111 个 = 111 个，
   **没有任何标识符只存在于坏文件里**。这样才能说"恢复版就是原始内容、
   负数验证期间没有别的改动"，而不是"看起来像"。
4. 恢复后验证：`node --check` exit 0、`node tools\bootstrap.mjs --check` **exit 0**
   （三步全 ✓）、`check-launchers` exit 0。

### 7l.4 三道防线（都落地了）

1. **启动器先说清楚"文件坏了"**：`tools\launch-gui.ps1` 在跑 bootstrap 之前先
   `& $node --check $bs`；不通过就打印 Node 原话前 5 行 + 「多半是源码下载 / 解压不完整，
   或者用记事本之类的编辑器保存过它（UTF-8 中文被当成 GBK 存坏）」+「重新下载一份完整源码覆盖本目录」。
   **"缺依赖"和"文件坏了"必须分开说** —— 处理方式完全不同。
2. **乱码哨兵**：`tools\check-launchers.mjs` 新增一节，扫 108 个文本文件
   （跳过 `node_modules` / `runtime` / `vendor`）找 20 多个 GBK 乱码特征字，
   命中就报红。反过来也做了**显式豁免**：`docs\08` §7i.1 必须照引用户那次报障的乱码原文
   （乱码本身就是证据），这类文件在开头写一行 `moji-scan:ignore` 声明豁免，
   **而不是让哨兵闭嘴**。负数验证做过：塞一个乱码文件进去 → exit 1 并点名文件；删掉 → exit 0。
3. **运行器不再把环境限制说成产品失败**：受限沙箱里 `spawnSync` 默认用管道收输出会被拒
   （EPERM），原来 17 套会"整整齐齐全红"。现在 `tools\run-all-tests.mjs` 遇到 EPERM
   自动改用**文件**接输出（普通文件不是命名管道），判据一个字不改；
   同时补了句提示：全是 EPERM 时**一行被测代码都没跑到**，别去查代码。
   （顺带修掉一个真 bug：失败报告里 `\`${stderr}\n${stdout}\`` 少了 `b.` 前缀，
   一旦真有套件跑不起来，运行器自己会抛 `ReferenceError` 把红行盖掉。）

### 7l.5 写完断言要"故意弄坏一次"

这三道防线里，有两个是**负数验证逼出来的**，而且其中一条差点白写：

- 新加的不变量「启动器会先 `node --check` 看 bootstrap.mjs」第一版写成
  `/--check\s+\$bs/`。**`\s` 能跨行**，而启动器里另有一行以
  `Say '【依赖清单（tools\bootstrap.mjs --check）】'` 结尾、下一行又以 `$bs` 开头 ——
  于是**把那句代码整段删掉，断言照样通过**。负数验证当场抓住（删了不报红），
  改成 `[ \t]+` 后：删掉 → exit 1 并点名；还原 → exit 0。
- 顺手把另外两条老不变量里的 `\s` 也收紧了（`&[ \t]*\$electron`、
  `Invoke-Electron[ \t]+'--version'`），同一个坑。

**教训**：断言"某句代码还在不在"时，空白一律写 `[ \t]+` / `[ \t]*`。
一条永远为真的断言比没有断言更危险 —— 它会让你以为这件事已经被守住了
（README 坑表里 `headless-multibot` 那条"闸门建在错对象上"是同一个道理）。

### 7l.6 诚实的边界

- 这次事故**是我造成的**，不是环境、不是用户、也不是上游。
  用户的每一次双击都真的撞在我留下的坏文件上（`第 2 步` 直接 SyntaxError）。
- 乱码哨兵只能发现**已经发生的**乱码；它拦不住"用 PowerShell 往返改文件"这个动作本身。
  真正的规则是**改文本只用 `edit` / `write` 工具或 `node -e`**。
- 恢复虽然验证得很严（0 条 ASCII 行丢失、标识符 111 = 111），但它的前提是
  "那次 `write` 的原文还在可反压缩的区块里"。**如果损坏发生在多次编辑之后、
  而那些编辑只存在于磁盘上，这条路就断了** —— 所以不要把"能反压缩"当成开发流程的一部分。

### 7m.3 ★ 冷跑抓到的真 bug：脚本承诺了一个不存在的分支

失败文案里写着「手动下载后放到 `runtime\node-v22.23.3-win-x64.zip`，再跑一次本脚本，
**它会跳过下载直接用这个 zip**」—— 而代码**从来没有检查过已存在的 zip**（总是先下载再覆盖，
失败就再退一次）。也就是说：**用户按这句话做，会掉进一个永远走不通的循环。**
文案和实现分居两个地方，只读代码看不出来，是"照着失败文案去做一遍"才暴露的。

修法三件事：
- 新增 `$preExisting = Test-Path $zip` 与 `if ($preExisting) { 跳过下载 }` 分支；
- 成功解压后**不再删用户自己放的那份 zip**（我们自己下的才删），并打印一句"你自己放的那个 zip 我留着没删"；
- 下载多一条路：`WebClient` 之外补 `curl.exe`（`-sS -L --fail --max-time 900`，
  `< 1MB` 一律判失败），两个源 × 两种方式都试过才认输，失败文案给出浏览器直链与放置路径。

**验证方式也是端到端的**：把现有 `runtime\node-v22.23.3-win-x64` 用
`tar.exe -a -cf …zip -C runtime node-v22.23.3-win-x64` 打成 35.9 MB 的"用户自己下好的 zip"，
放进冷目录的 `runtime\`，再跑 `bootstrap.mjs --yes --only node`：


## 七·补十、bot 受伤后掉线：不是门禁，是引擎抢在我们前面退了进程

### 7n.1 用户报障原文

> 现在发现一个现象：游戏内bot受伤后就会立马退出游戏，重启后再进入，疑似触发了门禁拦截

"疑似触发了门禁拦截"是个很合理的怀疑 —— 我们确实往引擎里塞了一层会在聊天这一级拦话的门
（`runner\mcbot-gate.mjs`）。但日志说不是。

### 7n.2 第一步取证：门禁是无辜的

- `runtime\logs\bot-xiaodou.out.log`（848 行，最后写入 2026-10-06 12:00:28）里，崩溃点前后的原文是：

  ```
  [MCBOT-GATE] BLOCK reason=rejectedSelf from=Xiaodou msg="我去找找煤矿，你站这儿别动呀。 "
  [LoginGuard] Disconnected: [object Object]
  Agent Xiaodou disconnected
  Agent process exited with code 1 and signal null
  Restarting agent...
  ```

  `rejectedSelf` 是"把 bot 自己说的话又回显给它自己"这一类**纯噪音**拦截（服务器回显），
  它不代表任何惩罚；而后面的断开是另一件事。
- 更硬的证据：自写的扫描器（`runtime\tmp\scan-kicks.mjs`）把
  `runtime\logs\bot-xiaodou.jsonl`（184 行）按类型统计，得到
  `{"log":9,"status":13,"mc":93,"gate":43,"llm":26}` —— **里面一条 `mc/kicked` 都没有，一条 `mc/end` 都没有**。
  而 `runner\event-log.mjs` 的 `emit()` 用的是 **`fs.appendFileSync`（同步写盘）**：
  只要监听器被调用过一次，记录就必然在磁盘上。没有记录 ⇒ **事件监听器根本没被调用** ——
  这才是要查的东西。

### 7n.3 真相：引擎用 `once('kicked'/'end')` 抢在我们前面 `process.exit(1)`

`vendor\mindcraft-develop\src\agent\agent.js:69-89`（在 `start()` 里注册，**早于**
我们的门挂监听器的时机 `_setupEventHandlers`，见 `agent.js:122` 与 `runner\mcbot-gate.mjs:1199-1204`）：

```js
const onDisconnect = (event, reason) => {
    if (this._disconnectHandled) return;
    this._disconnectHandled = true;
    const { type } = handleDisconnection(this.name, reason);
    process.exit(1);
};
this.bot.once('kicked', (reason) => onDisconnect('Kicked', reason));
this.bot.once('end', (reason) => onDisconnect('Disconnected', reason));
```

Node 的 `EventEmitter` 按注册顺序调用（同优先级下先注册先跑）⇒ **引擎的回调先跑并在里面直接退出进程**，
我们后注册的 `bot.on('kicked'/'end')` 永远轮不到。于是：

- 用户看到的是"受伤 → 立刻退出游戏"；日志里看到的是 `[LoginGuard] Disconnected: …` + 引擎自己重启；
- 我们的应用（`app\electron\supervisor.mjs`）按设计做了退避重连（`3s × 2^n`，上限 60s，滚窗口内最多 5 次），
  用户在游戏里看到的就是"重启后再进入"，而每次进去一两秒内又被服务器断开 —— 三次之后
  `Agent process exited too quickly and will not be restarted.`

**所以那句"受伤"与"退出"之间没有门禁这一环**：门只拦聊天文本，从不主动断线。
但"为什么会被服务器断开"仍然**没有答案** —— 这就要先让原因能被打出来。

### 7n.4 `Disconnected: [object Object]` 是怎么来的

`vendor\mindcraft-develop\src\agent\connection_handler.js`：

- 它有一张关键词表 `ERROR_DEFINITIONS`（`duplicate_login` / `whitelist` / `server is full` /
  `timeout` / `flying` / `spam` 等）。命中就 `console.error(\`Disconnected: ${raw}\`)`。
- **没命中**就走
  `fallback = obj.translate || obj.text || (obj.value?.translate) || raw;`
  → `{ type:'other', msg: \`Disconnected: ${fallback}\`, isFatal:true }`。
- 而 1.21.1 的 kick 原因是 protodef 解出来的
  `{type:'compound', value:{translate:{type:'string', value:'multiplayer.disconnect.xxx'}}}` ——
  `obj.value.translate` 是**一个对象**，塞进模板字符串就成了 `[object Object]`。

换句话说：**引擎打印出了"我没认出这个原因"这个事实，但把原因本身丢了。**
未命中关键词的可疑候选是 `multiplayer.disconnect.invalid_player_movement`
（原版提示 `Invalid move player packet received`，与我们本地测试服踢客户端 11 次的那条一致）
或 `multiplayer.disconnect.kicked`（管理员/插件踢）—— 但**这只是怀疑，不是结论**。

### 7n.5 修法：先让原因能落盘，再让它变成人话

1. **抢到最前面**（`runner\mcbot-gate.mjs`）：不再用 `bot.on`，改用
   `bot.prependOnceListener('kicked' | 'end', …)`。它是**同步**写事件的
   （`emit` → `appendFileSync`），所以引擎即使紧接着 `process.exit(1)`，记录也已经落盘：

   ```js
   const noteDisconnect = (kind, reason) => {
       const cn = describeKick(reason);
       const raw = (typeof reason === 'string' ? reason : JSON.stringify(reason ?? null)) || '';
       emit('mc', { kind, reason: cn, raw: raw.slice(0, 400) });
       emit('log', { level: 'warn', line: `[MCBOT-KICK] ${kind} ${cn}（原始：${raw.slice(0, 200)}）` });
       console.log(`[MCBOT-KICK] ${kind} ${cn}（原始：${raw.slice(0, 300)}）`);
   };
   bot.prependOnceListener('kicked', (reason) => noteDisconnect('kicked', reason));
   bot.prependOnceListener('end', (reason) => noteDisconnect('end', reason));
   ```

2. **把 protodef 那层壳翻成人话**：新模块 `runner\kick-reason.mjs`
   （`KICK_REASONS` 约 15 条官方 key→中文、`flattenChat` 吃 compound/translate/string/text/extra、
   深度上限 6、`decodeKick`、`describeKick`）。
   `describeKick` 的硬承诺：**永不返回空、永不返回 `[object Object]`**；
   认不出的 key 就原样说"服务器给的原始原因：`multiplayer.disconnect.xxx`" ——
   宁可难看，也不许编。表里那条 `multiplayer.disconnect.invalid_player_movement` 译成
   "服务器认为我们的位置数据不对（被击退、掉下去的那一瞬间最容易触发）"。
3. **面板与日志也说人话**（`app\electron\supervisor.mjs` 的 `readExitReason`）：

### 7n.6 单测当场抓住一个真 bug；不变量也当场被负数验证检验过

### 7n.7 意外收获：发布体检抓出一次真实的隐私泄露

跑全量自检（`runtime\tmp\allsuites-b162.log`）时 **`check-publish` 红了 13 条**，
点名这些文件里有**用户真实游戏 ID**：

```
runner/profiles/bot-xiaodou.json:5
vendor/mindcraft-develop/bots/Xiaodou/histories/2026-10-611-55-05.json
vendor/mindcraft-develop/bots/Xiaodou/last_profile.json
vendor/mindcraft-develop/bots/Xiaodou/memory.json
```

`runner/profiles/<botId>.json` 是**启动器每次运行时按配置重新生成的**
（`runner\engine-launcher.mjs` 的 `PROFILES_DIR`，`app\electron\paths.mjs` 也指这里），
里面写着主人名单，也就是用户的游戏 ID。它本来被跟踪进了首个提交，
然后用户在真机上跑过一次之后，工作区里的版本就带上了真实 ID —— 再 `git add .` 就是一次泄露。

**先核实"有没有已经发出去"**：对已推送的 `4bb2c8b` 做
`git grep -l -F 'Exus1ai' 4bb2c8b` → 只命中 `LICENSE` 与 `docs/09-…md`，
那是**作者署名** `Exus1ai`，不是**游戏 ID**（原文里写的是你的真实 ID，这里已脱敏 ——
发布体检会从 `runtime\config.json` 的 `owners` 读你的 ID 来比对，所以文档里一律不写它）。
**结论：游戏 ID 没有进过任何提交，没有被发布出去。**

修法：`.gitignore` 增加 `runner/profiles/`（带说明注释），
并 `git rm --cached runner/profiles/{bot-axiao,bot-xiaodou,spike}.json` —— 文件照旧在本地生成，只是不再入库。

### 7n.8 同一片红色里还混着**假红线**，那更贵

另一半红色不是泄露：`vendor\mindcraft-develop\bots\Xiaodou\*` 是引擎运行时生成的，
而我们自己的发布体检说它"会提交"。原因是**体检里的 `.gitignore` 解析器有两个 bug**：

1. **只读根目录那一份**，所以引擎自己 `.gitignore` 里的 `bots/**/` 完全没生效；
2. `globToRe()` 把每个 `*` 都翻成 `[^/]*`，于是 `bots/**` 只能匹配 `bots/` 下面的**一层**，
   子树里的文件全漏。

修法：`loadIgnoreRules(prefix = '')` 支持按目录加前缀读取，`walk()` 改成 DFS
（进目录时 push 这份子树的规则，`finally` 里按同样条数 pop，保证只在这一棵子树生效）；
`globToRe()` 单独处理 `**`：

```js
const conv = (s) => s.split('/').map((seg) => seg.split('*').map(escapeRe).join('[^/]*')).join('/');
return new RegExp('^' + glob.split('**').map(conv).join('.*') + '$');
```

修完：`node tools\check-publish.mjs` → **EXIT=0**，`会提交：文件 303 个，共 3.90 MB`，
红线一条不剩；并且和 git 自己的口径交叉核对过
（`git ls-files --cached --others --exclude-standard` 数出来也是 **303**）。

**为什么要在这里单独写一段**：假红线会让人开始怀疑体检本身 ——
真泄露那条就混在同一片红色里，一旦学会"这些红的是噪音，忽略就好"，真那条也会被一起忽略。

  真正的原因要靠用户在真机上复现一次，再把日志里那行 `[MCBOT-KICK] …` 发回来。
  在那之前我不会猜一个"大概是 xxx"填进结论（`invalid_player_movement` 只是**候选**）。

## 七·补十一、掉线的真因：我们往服务器发了一个"非法移动包"（NaN / 重生后立刻回包）

上一节（§七·补十）做到的是"把断线原因抓回来"，结论是**当时原因未知**。这一节是把它查到底，
并且**改成不再发生**。

### 7o.1 先把"受伤"这个前提去掉

`runtime\logs\bot-xiaodou.jsonl` 里每 10 秒一条 `mc/stats`（含血量），那一次运行的原文是：

```
11:59:52  hp=20 food=19
12:00:02  hp=20            ← 用户在这之后攻击了 bot
12:00:06  status starting  ← 新进程（上一次会话已经死了）
12:00:08  login + spawn（位置还是 -46.5, 76, -12.6）+ hp=19
12:00:18  hp=20 food=17    ← 位置一模一样，一点没挪
12:00:24  status starting  ← 又死了
```

**血量从没掉到 19 以下，位置纹丝不动，一条 `mc/death` 都没有。** 空手打一下只掉 1 点血，
"hp=19" 是上一次会话遗留的血量，不是致死。"用户攻击 bot"与"掉线"只是**同时发生**。

于是症状要重新描述成：**每次上线约 10~16 秒后，被服务器以"非法移动包"为由踢掉。**
（stdout 里没有时间戳，`[LoginGuard] Disconnected` 在文件里紧跟着门禁装载那行，
但 jsonl 证明进程活到了 18 秒 —— **别被日志的相邻行误导。**）

### 7o.2 三条互相独立的证据

1. **本地测试服日志**（`testserver\logs\latest.log`）：全文件 11 次
   `lost connection: Invalid move player packet received`（行 509 / 519 / 590 / 808 / 866 / 871 /
   1549 / 1635 / 1656 / 1659 / 1663）。**被踢的全是 mineflayer 客户端** —— 既有我们自己的 bot，
   也有纯 mineflayer 写的自检测试玩家（Steve / Alex，有一次它只活了 **1 秒**）。
   这直接排除了"我们的门禁/我们的代码造成的"。
2. **上游 issue 与 PR**：[#1467](https://github.com/PrismarineJS/mineflayer/issues/1467)
   标题就是 `bot.lookAt() is writing packet with pitch NaN leading to disconnect`；
   [PR #4130](https://github.com/PrismarineJS/mineflayer/pull/4130) 写明"字段 undefined 会被序列化成 NaN，
   服务端的 `containsInvalidValues()` 会拒掉"；PR #3863 / #3865 是上游 CI 里同一个错。
   服务端那句 `Invalid move player packet received` 对应的就是
   `multiplayer.disconnect.invalid_player_movement`（这门禁里早就有一条中文翻译，见 §7n.5）。
3. **上游源码**：mineflayer master 的 `lib/plugins/physics.js` 比我们钉的 4.33.0 多出两类守卫，
   注释写得很直白：

   ```js
   // Don't send position with invalid coordinates (NaN after death)
   // After death/respawn, delay the forced position_look response.
   // Sending it immediately causes "Invalid move player packet" kicks
   // on older servers, but the server needs it to complete the respawn.
   ```

### 7o.3 改了什么

全部落在 `vendor\mindcraft-develop\node_modules\mineflayer\lib\plugins\physics.js`（453 → 522 行），
并已并进 `patches\mineflayer+4.33.0.patch`（55 → 202 行，涉及 4 个文件 / 11 个 hunk）：

| 位置 | 守卫 |
| --- | --- |
| `tickPhysics` 开头 | `if (bot._client.state !== 'play') return` + 位置有限性检查 |
| `sendPacketPosition` | 状态判断 + `x/y/z` 有限性（上游有） |
| `sendPacketLook` | 状态判断 + **yaw/pitch 有限性（上游没有，我们补的）** |
| `sendPacketPositionAndLook` | 状态判断 + 位置 + **yaw/pitch（上游没有）** |
| `updatePosition` | `isEntityRemoved()` 之后加"死后 NaN 不发"（上游有） |
| `bot.look` 入口 | **拒绝非有限角度，不让它污染 `bot.entity.yaw`（上游没有）** |
| 服务端 `position` 包处理 | 死亡/重生后 1.5 秒再回那个强制的 `position_look`（上游有） |
| `cleanup()` / `bot.on('death')` | 配套的 `respawnTimer` / `respawnReply` |

**为什么额外补朝向那三条**：上游只防"位置 NaN"。而 `updatePosition` 里那句
`lastSentYaw += math.clamp(-maxDeltaYaw, dYaw, maxDeltaYaw)` —— 一旦 `bot.entity.yaw` 被写成 NaN，
它会**永久留在 `lastSentYaw` 里**，此后每一帧发出的 `look` / `position_look` 都带 NaN，
也就是"一直被踢、重连上去十几秒又掉"。必须在**源头**（`bot.look`）拦住，而不是拦在出口。

坏值一律走 `noteBadMove()` 打一条 `[MCBOT-PATCH] 拦下一个非法移动包（…）：数值 = …`，
**5 秒内只打一条**（免得刷屏糊掉关键行）。这行日志是给真机复现准备的：它一出现，
就说明"坏值确实存在、而且已经被拦住"。

### 7o.4 离线把补丁并进 `patches\`（patch-package 要联网，本沙箱 npm 不通）

1. **先拿到权威的原始文件**：`registry.npmjs.org` 连不上（`UND_ERR_CONNECT_TIMEOUT`），
   但 npm 缓存里有 —— `.npm-cache\_cacache\index-v5\…` 里 key 为
   `make-fetch-happen:request-cache:https://registry.npmjs.org/mineflayer/-/mineflayer-4.33.0.tgz` 的那条
   指向 `content-v2\sha512\b7\2b\14295854…`（333,899 字节），`tar -xzf` 解出来就是 4.33.0 原版。
2. **先证明基线对得上**：把**现有** patch `git apply -p1` 到原版上，
   得到的 `digging.js` / `inventory.js` / `place_block.js` 与**已安装文件逐字节相同**。
3. **改完再生成**：在临时仓库里"原版当基线提交 → 覆盖成改好的文件 → `git diff --output=<文件>`"。
   然后与现有 patch 拼成 `.new`，再拿一个**全新的原版树**打一遍 `.new` →
   **4 个文件全部与已安装逐字节相同**（等于替用户机器上的 `npm ci` + patch-package 先走了一遍）。
   通过后才把 `.new` 覆盖成正式的 patch 文件。

踩到的三个坑（都写进 README 坑表了）：

- ⚠️ **别用 PowerShell 的 `>` 重定向写 patch**：Windows PowerShell 5.1 写出来是 UTF-16LE，
  读回来是 `��d i f f`。用 `git diff --output=` 由 git 自己写 UTF-8。
- ⚠️ 临时仓库必须先 `git config core.autocrlf false`（本机全局是 true），否则整个文件被视作改动，
  diff 里会出现"某文件 264 行全替换"的假差异。
- ⚠️ **不要手工"反推"原始文件**：我先写了个脚本按字符串反向替换还原原版，行数多了 1 行，
  `git hash-object` 得到 `26920b7a…`，而 diff 头里写的是 `0bcf679…` —— 当场被抓。
  **能拿到权威原件就绝不靠反推。**

### 7o.5 能跑起来的检查

新增 `tools\test-physics-guards.mjs`（22 项，已登记进 `tools\run-all-tests.mjs`）。它不只查字符串，
而是**把 physics.js 真的注入一个假 bot 跑起来**：

- `bot.look(NaN/undefined)` → 一个包都不发、`bot.entity.yaw` 不被污染、日志里有那行中文告警；
- 正常的 `bot.look(1.0, 0.5, true)` **照旧生效**（守卫不能把好值也拦了）；
- 正常的服务端传送照旧回 `teleport_confirm` + `position_look` + `forcedMove`；
- 传送包里是 NaN → **不发** `position_look`（这正是踢人的那一包）；
- 坐标是 NaN 时物理循环跑 5 帧 → 一个坏包都不发、不抛异常；
- 死亡后**立刻**不发、**1.5 秒后**补上那个 `position_look`。

两处工程细节：**15 秒总闸**（守卫丢了的话 `await bot.look(NaN)` 会永远等一个不会来的事件，
卡死比报错难查；故意不 `unref()`，否则事件循环空掉时 Node 会以 0 退出，把"卡死"粉饰成"通过"），
以及**负数验证**：把安装的那份换成 npm 原版 → 5 条静态断言红 + 动态部分卡到总闸报红（EXIT=1），
换回来 SHA256 与改前一致。

`tools\bootstrap.mjs` 的 `PATCH_EVIDENCE` **5 → 9 条**（新增 `function noteBadMove`、
`// Don't send position with invalid coordinates (NaN after death)`、`respawnTimer`，
以及一条**中文串** `拦下一个非法移动包` —— 英文串还在时中文串会先烂掉，它专门用来抓"文件被存成 GBK /
patch 被写坏"），`tools\check-launchers.mjs` 的 needle 列表同步。

### 7o.6 诚实的边界

- **真机尚未验证。** 用户机器上跑的是这份工作区，**重启应用即可生效**（不必先推送）。
  最终判据是复现后日志里那行 `[MCBOT-KICK] …`；如果它写的是
  `invalid_player_movement`（服务器认为位置数据不对），并且同时出现
