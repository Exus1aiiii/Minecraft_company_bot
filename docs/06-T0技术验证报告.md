## 二、协议栈错配（本阶段最耗时的问题，值得完整记录）

### 2.1 现象

引擎能起、MindServer 能连、`Examples initialized.`，但一登录就死：

```
Error getting server: TypeError: Cannot read properties of null (reading 'version')
    at ping (…\minecraft-protocol\src\ping.js:26:26)
Timeout pinging server 127.0.0.1:25565
Attempting to connect anyway...
unsupported protocol version: 26.1
    at Object.createClient (…\minecraft-protocol\src\createClient.js:30:22)
    at createBot (…\mineflayer\lib\loader.js:103:35)
    at initBot (…\src\utils\mcdata.js:68:17)
```

### 2.2 第一层：`defaultVersion` 与 `minecraft-data` 不相交

```js
// minecraft-protocol/src/createClient.js
:24  if (!options.version && !options.realms) { options.version = false }
:27  // TODO: avoid setting default version if autoVersion is enabled
:28  const optVersion = options.version || require('./version').defaultVersion
:29  const mcData = require('minecraft-data')(optVersion)
:30  if (!mcData) throw new Error(`unsupported protocol version: ${optVersion}`)
...
:69  if (options.version === false) autoVersion(client, options)
```

`ping.js:24` 走的是一模一样的兜底逻辑，所以 `mcserver.js` 的 `serverInfo()` 探测一起挂掉。

关键点：**兜底版本的校验（`:30`）发生在 `autoVersion()`（`:69`）有机会纠正版本之前。**
`minecraft-protocol@1.68.0` 的 `defaultVersion = '26.1'`，而当时被钉死的 `minecraft-data@3.97.0` 最高只到 1.21.8 → `require('minecraft-data')('26.1')` 返回 null → 必死。

**为什么走不到显式版本**：`src/utils/mcdata.js:11` 是

```js
let mc_version = settings.minecraft_version;   // 模块级快照，import 时定值
```

而 agent 子进程要等 `serverProxy.connect()` 的 MindServer 握手才拿到真正的 settings —— 那一刻 `mcdata.js` 早就 import 完了，`mc_version` 永远是 `undefined`，于是 `:64-65` 执行 `delete options.version`。**子进程永远走自动探测**，兜底版本就是它的唯一依靠。

### 2.3 第二层：`minecraft-data` 被 overrides 压到了所有依赖方的最低要求之下

```
mineflayer@4.33.0        声明 minecraft-data ^3.98.0
minecraft-protocol@1.68.0 声明 minecraft-data ^3.109.0
prismarine-registry@1.12.0 声明 minecraft-data ^3.70.0
prismarine-block@1.23.0    声明 minecraft-data ^3.38.0
minecraft-data 实装        3.97.0   ← 低于前两者的最低要求
```

而且更硬的一刀来自 `prismarine-chunk@1.41.0`（`mineflayer@4.33.0` 声明 `prismarine-chunk: ^1.39.0`，于是装到了 1.41.0）：

```js
// prismarine-chunk/src/pc/1.18/ChunkColumn.js:15
const hasFluidCount = mcData.version['>=']('26.1')
```

`minecraft-data/index.js:43` 对未知版本是**硬抛**：

```js
const raise = other => { throw new RangeError(`Version '${other}' not found in [...] for ${type}`) }
this['>='] = other => versions[other] ? v1 >= versions[other].dataVersion : raise(other)
```

→ 只要 `minecraft-data` 不认识 `26.1`，**任何版本**的连接都会在注入 mineflayer 插件时抛 `RangeError`。这与 `defaultVersion` 无关，纯靠配置修不好。

### 2.4 修法

**(a) 把 `minecraft-data` 上移到 3.117.0**（满足最严的 `^3.109.0`）：
`vendor/mindcraft-develop/package.json` 的 `dependencies` 与 `overrides` 同步改。

**(b) 上游的 `patches/minecraft-data+3.97.0.patch` 已过期，移入 `patches-disabled/`。**
它改的是 1.21.6 `protocol.json` 里 `checksum` 的 `i8` → `u8`；**3.117.0 里上游已经自己修成 `u8`**（本机实测），所以这个补丁不再需要，且版本号对不上会被 patch-package 拒绝。
→ 仍在生效的补丁只剩 4 个：`mineflayer+4.33.0` / `mineflayer-pathfinder+2.4.5` / `mineflayer-pvp+1.3.2` / `protodef+1.19.0`。

**(c) 新增 V-3 守卫兜住这一类问题**（`runner/engine-patches.mjs`）：
在注入时把 `minecraft-protocol/src/version.js` 的 `defaultVersion` 改成"`minecraft-data` 确实有数据"的版本 —— 优先用配置里的具体版本，`auto` 时退到"认识的最高版"。
之所以改属性而不是打补丁：`createClient.js:28` 与 `ping.js:24` 都是**调用时**读 `require('./version').defaultVersion`，CJS 模块对象在同一份 require 缓存里，改属性即全进程生效，且**完全不动 node_modules 里的文件**（`npm install` 冲不掉）。
`autoVersion.js` 实测会把 `options.version` / `options.protocolVersion` / `client.version` 全部纠正成服务端真实版本，所以兜底值只需"有数据 + 尽量接近目标"（`options.majorVersion` 不会被改写，它决定 mineflayer 的 dataPaths 选择，所以要用目标版本而非最泛的版本）。

### 2.5 教训（写进 `docs/05`）

1. **上游把 `package-lock.json` 写进 `.gitignore` 这件事的杀伤力远超预期。** 它不是"少个文件"，而是让 `patches/` 整套机制在全新安装时必然失效：补丁文件名里的版本号（`minecraft-data+3.97.0`）成了错误的版本锚点，而 `^` 范围会把依赖拉到与之不兼容的新版本。**我们保留 lockfile 的决定是对的。**
2. **"补丁涉及的包钉死"这个策略本身有坑**：钉死的版本可能已经低于其下游依赖声明的最低要求。钉之前必须校验 `engines` 与 `dependencies` 区间，`tools/probe-protocol-stack.mjs` 的第 3 条判据就是干这个的。
3. **症状在 A 层，根因常在 B 层**：报错指向 `defaultVersion`，真正的死因是 `prismarine-chunk` 里一行 `mcData.version['>=']('26.1')`。

## 三、聊天门实测证据

配置：`runner/bots/spike.bot.json` → agentName `Xiaodou`，wakeNames `["小豆","xiaodou","豆豆"]`，owners `["Steve"]`，rateLimitMs 3000。

| 玩家 | 消息 | 门的判定 | 大模型调用 |
|---|---|---|---|
| Steve（owner） | `大家晚上好，今天天气不错` | `BLOCK reason=rejectedNoWakeName` | **0** |
| Steve | `小豆 你好呀，能听见我说话吗` | `PASS channel=chat`，cleaned=`你好呀，能听见我说话吗` | 1 |
| Steve | `/msg Xiaodou 你在忙什么呢` | `PASS channel=whisper`（免称谓） | 1 |
| Xiaodou（bot 自己） | `你好呀，我是小豆，我在这儿呢。` | `BLOCK reason=rejectedSelf` | **0** |
| Alex（非 owner） | `小豆 你也来帮我建个房子吧` | `BLOCK reason=rejectedNotOwner` | **0** |
| Alex | `xiaodou stop` | `BLOCK reason=rejectedNotOwner` | **0** |

对应的验收标准：**A2 与 A5 通过**。原始日志：

```
[MCBOT-GATE] installed on agent=Xiaodou removedEngineListeners=2 wakeNames=["小豆","xiaodou","豆豆"] owners=["Steve"] rateLimitMs=3000
[MCBOT-GATE] BLOCK reason=rejectedNoWakeName from=Steve msg="大家晚上好，今天天气不错"
[MCBOT-GATE] PASS channel=chat from=Steve raw="小豆 你好呀，能听见我说话吗" -> cleaned="你好呀，能听见我说话吗"
Xiaodou received message from Steve : 你好呀，能听见我说话吗
[MCBOT-LLM] awaiting http://127.0.0.1:8799/v1 model=mcbot-spike-model
Generated response: 你好呀，我是小豆，我在这儿呢。
[MCBOT-GATE] BLOCK reason=rejectedSelf from=Xiaodou msg="你好呀，我是小豆，我在这儿呢。 "
```

**结论：这套"不改引擎源码、只注入一层门"的架构成立。** 关键在于 `agent.js` 把 `respondFunc` 闭包同时存成了实例属性 `this.respondFunc`，外部才有干净的调用入口。
