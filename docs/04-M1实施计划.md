## 一、M1 目标与验收标准

**一句话目标**：在**离线模式 + Minecraft 1.21.1（Fabric 服务端）**上跑起**一个** bot，用户能在我们自己的像素风 GUI 里填模型 API、开关 bot；在游戏聊天框里用**限定称谓**叫它，它能用人格化的中文回话，并能在被要求时跟随玩家。

> **版本修订（2026-10-05，`m00331`）**：原定 MC 1.21.6，但用户手头服务器的实际上限是 **1.21.1 + Fabric**。1.21.1 仍在引擎支持区间内（Mindcraft ≤1.21.11，mineflayer 1.8→26.1 且自动探测版本），**仍不需要 ViaProxy**；但它**不是引擎的官方推荐版本**，所以"1.21.1 冒烟实测"被提为 **T0 的第一项**。

> **版本修订（2026-10-06，`m11702`）**：用户要求"兼容更多 MC 版本，第一步 1.20.1"。做法与证据见
> `docs\08` §七·补十三：版本判断收成一处（`runner\mc-versions.mjs`）、逐版本核对按名字写死的表
> （`tools\test-versions.mjs`）、界面上填错当场说人话。**1.20.1 目前只到"数据核对过"**
> （本机下不到这一版的服务端 jar），真连过并因此"真支持"的仍只有 1.21.1 —— 这一条是与上面那句
> "1.21.1（锁定）"的关系：**锁定没变，只是不再是唯一能填的版本**。

| # | 验收信号（用户可亲自复现） |
|---|---|
| **A1** | 在 GUI 里填好 Base URL / Key / Model，点"启动"，bot 出现在服务器里 |
| **A2** | 在聊天框说"**（称谓）你好**" → bot 用中文、以设定的人格回话；**没带称谓的闲聊，bot 完全不响应、且不消耗 token** |
| **A3** | 在聊天框说"**（称谓）跟着我**" → bot 跟随玩家移动 |
| **A4** | 在 GUI 里关掉开关 → bot 下线；再打开 → bot 重新上线 |
| **A5** | 服务器上有**第二个玩家**（或用一个测试账号）说同样的话 → bot **不响应**（owner 门生效） |
| **A6** | GUI 面板能看到 bot 状态、最近日志、以及本次会话的 token 消耗 |

> A5 与 A2 的后半句是**这个项目的核心差异点**，必须进 M1 验收——引擎本身两者都做不到（见文档 03 §9.1–9.3）。

## 二、M1 明确**不做**的（防范围膨胀）

| 不做 | 归属 | 理由 |
|---|---|---|
| 聊天接建造委托 / 蓝图建造 | M4 | 需要任务编排 + 进程重启链路，是独立的大模块 |
| 长期陪伴记忆 / 向量检索 | M3 | 需要 SQLite + 嵌入模型，且引擎侧无可复用基建 |
| 自然语言 → 多步任务分解 | M2/M3 | M1 只做"唤醒 + 对话 + 少量固定意图" |
| 多 bot / 多服务器并行 | M4 | 但 M1 的**进程模型必须一开始就是 Supervisor + Runner**，否则 M4 要重写 |
| 皮肤实际生效 | M5 | M1 只在 GUI 里存配置并显示"生效条件"，不做真实换肤 |
| 3D 世界预览 | 决策 7 | 不引入 three.js |
| ViaProxy 跨版本 | 预留 | 版本锁 1.21.6 |
| 安装器 / 打包分发 | M5 | M1 只跑开发模式 |
| MCP 接入（Claude/Cursor 直连） | 附加能力 | 与 M1 主线无关 |

## 三、M1 架构（收敛版）

```
┌─ Electron 主进程 ────────────────────────────┐
│  Supervisor（注册表 / 进程守护 / 重启退避）    │
│  Credential（safeStorage → DPAPI）            │
│  LLMGateway 薄层（限流 / 预算 / token 计数）   │
└───────┬──────────────────────────────────────┘
        │ stdio JSON-RPC（子进程）
┌───────▼──────────────────────────────────────┐
│  Runner 进程（Node 20 LTS，M1 只有 1 个）      │
│   ├ profile JSON 生成 → 交给引擎               │
│   ├ import vendored mindcraft 引擎            │
│   │    └ 1 个 Agent（1 个 mineflayer bot）     │
│   └ ★ 聊天门（本项目的第一个自研补丁）          │
│        chat/whisper 监听器接管：                │
│        owner 校验 → 唤醒称谓 → 限流 → 转发      │
└──────────────────────────────────────────────┘
┌──────────────────────────────────────────────┐
│  渲染进程：React + 纯 CSS 像素风 UI            │
└──────────────────────────────────────────────┘
```

### 3.1 与引擎的接合方式（M1 第 0 步必须先定论的技术分叉）

引擎的 `main.js` 是"**应用入口**"而非库（`package.json` **无 `main`/`exports`**），它自己收 `yargs`、自己 `Object.assign(settings, ...)`、自己 `Mindcraft.createAgent()`。我们要在 agent 起来**之后**接管它的 `chat`/`whisper` 监听器，所以有两条路：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A（首选）自建 Runner 入口** | 不走 `main.js`；我们的 `runner.js` 用相对路径 `import { Mindcraft } from '<vendor>/mindcraft/src/mindcraft/mindcraft.js'`，自己 `Mindcraft.init(...)` + `Mindcraft.createAgent(settings)`，随后 `bot.removeAllListeners('chat'/'whisper')` 并挂上我们的门 | **零源码改动**，引擎可整体升级 | 依赖引擎模块能被独立 import（可能有单例/副作用耦合）；需实测 |
| **B（兜底）单点补丁** | 仍走 `main.js`（`SETTINGS_JSON` 注入），在 vendored 引擎里改 `src/agent/agent.js` 的 `_setupEventHandlers`，把 `respondFunc` 的调用处改为经过一个可注入的 hook | 行为确定、易调试 | 引擎升级要重打补丁；补丁必须集中、可测试 |

**推荐**：M1 的 **T0 spike 用半天实测方案 A**。判定标准：能否在不改动引擎源码的前提下，让一个自写入口成功 `createAgent` 并拿到 `agent.bot`。成功则 A，失败则退 B（B 也可接受，因为我们本来就是 vendor 而非 npm 依赖）。

> 无论 A/B，**接管点都是同一个**：`agent.js` 把 `respondFunc` 存成了实例属性（`this.respondFunc = respondFunc;`），所以外部可以复用它的完整逻辑，只在我们自己的门之后调用它。这是文档 03 §9.2 的发现，是 M1 能低成本实现唤醒称谓的关键。

### 3.2 唤醒与权限的具体规则（M1 版）

`gate(username, message)` 按顺序：

1. **owner 校验**：`username === config.owner.name`（离线服无 UUID，只能按名字；**因此必须同时支持"仅接受私聊"模式**作为更强的隔离手段——决策 8 的 "owner 比对要防伪装"）。
2. **唤醒称谓匹配**：消息包含 `config.bot.wakeNames`（默认 = bot 名 + 用户自定义别名，中文）。
3. **限流**：每 `N` 秒最多唤醒一次（默认 5s，可配）；且当日 token 预算未超。
4. **命中 → `agent.respondFunc(username, message)`**；**未命中 → 直接 `return`，不写 history、不调模型**（这就是"零 token"的实现处）。

**"跟着我"这类固定意图**在 M1 **不走模型**：在 gate 命中后先用**中文字符串规则匹配**（如 `/跟着我|跟紧我|follow me/` → `!followPlayer(<owner>)`），命中则直接执行引擎命令（零 token），未命中才把整句交给模型。这样 A3 的验收不依赖模型质量，也顺带压住成本。**模型意图识别留给 M2。**

## 四、任务分解（按依赖顺序，T0 是唯一的关键路径分叉）

### T0 · 运行时与引擎落地（spike，最先做，决定后续所有事）
- 用 **Node 20 LTS** 建工程骨架；把 mindcraft **vendor** 到 `vendor/mindcraft`（**保留 `patches/`**，`postinstall` 依赖它）。
- **实测 Node 24 是否真的崩**：在 Node 24 下装依赖并启动，记录具体报错（这是"必须自带 Node 20/22 LTS 运行时"这一决策的**证据**；注意 `spawn` 时**无条件调用 `addBrowserViewer`**，渲染依赖一定会被拉起——文档 03 §9.7）。
- **spike 方案 A/B**（见 §3.1）。
- **实测 `language` / 翻译链路**（见第五节 R-1，这是最高风险项）。

### T1 · 配置与凭据
- `config.json`（模型 / 服务器 / bot / 策略 / 唤醒称谓 / owner）+ `keys.json`（**不入库**）。
- 密钥经 Electron `safeStorage`（Windows DPAPI）加密落盘；**渲染进程永不接触明文 key**。
- **profile JSON 生成器**：把 GUI 的配置映射成引擎 profile（`name`、`model`、中文 `conversing` 人格、`only_chat_with`、`load_memory:false` 等）。
- 🔴 **代码层拒绝透传 `INSECURE_CODING`**（决策 3 的落地）。强制 `allow_insecure_coding: false`，且**该配置项在 UI 与 config 中都"不存在"**，而非"默认关"。

### T2 · Supervisor + Runner 生命周期
- Supervisor：spawn / stop / restart Runner；stdio JSON-RPC。
- **进程守护 + 指数退避重连**——必须，因为引擎会因 `spawn_timeout`、`kicked`、`end`、`!smeltItem`、`!restart` 主动 `process.exit(1)`（文档 03 §9.6）。
- UI 状态机：`启动中 / 在线 / 正在重启 / 重连中 / 已停止 / 错误`；**引擎自重启不得表现为"掉线"**。

### T3 · ★ 聊天门（本项目第一个核心自研模块）
- 接管 `chat` / `whisper` 监听器（§3.1、§3.2）。
- owner 校验 + 唤醒称谓 + 限流 + 非唤醒丢弃。
- **绕过引擎"多于 1 个 agent 就忽略公屏"的逻辑**（文档 03 §9.2）——M1 虽是单 bot，但门要按"多 agent 也应该正常工作"来写，否则 M4 返工。
- 关闭 `SelfPrompter` 自动自我提示（默认关，否则持续烧 token）。

### T4 · 中文人格与对话
- profile 的 `conversing` 提示词写为**中文陪伴型人格**模板；GUI 上可编辑（"人格面具"）。
- `settings.language = "zh"`。
- **成本瘦身**三处（文档 03 §9.4）：`show_command_syntax`（命令表注入）、行为日志 500 字符/条、`max_messages`/`relevant_docs_count` 的检索注入。

### T5 · 跟随（A3）
- 规则匹配"跟着我" → `!followPlayer(<owner>)`；"别跟了/停下" → `!stop`。
- 接入 `mineflayer-pathfinder` 的 **`createHuman(bot, {seed})`**（文档 02 §4.6：拟人行走、真实鼠标网格转头、seed 派生每 bot 性格）→ 同时解决反作弊像人 + 为 M4 的多 bot 差异化打底。
- 注意 `!attack` 的 `kill` 恒为 true（文档 03 §八），M1 不用战斗。

### T6 · 像素风 GUI
- 主界面分区：**服务器**（可增删的多行表格，M1 只用第一条但布局按多服设计）、**模型 API**（Base URL / Key / Model / 预设）、**bot**（名称、唤醒称谓、皮肤配置+生效条件提示）、**人格面具**（提示词编辑）、**开关**（在线/离线 + 休眠档）、**日志与费用面板**。
- 像素风实现：CSS 变量 + `image-rendering: pixelated` + 九宫格边框。
- ⚠️ **不得直接使用 Minecraft 原版纹理 / 音效 / 皮肤**（版权，见文档 02 合规表）；像素美术自绘或采用可商用资源。
- 中文像素字体（文档 01 风险 R18）——优先用**开源可商用**的中文像素字体，避免嵌入商业字体。

### T7 · 成本与可观测
- token 计数 + 费用估算（按模型单价表）+ 当日累计；超阈值拦截。
- 日志面板：转发引擎 stdout/stderr；把"进程重启"渲染成明确的事件行。
- **"休眠"档**：在线但不主动决策、只响应唤醒（决策 5 的省 token 默认手段）。

### T8 · 验收
- 按第一节 A1–A6 逐条手测并记录。
- 记录第五节 R-1 ~ R-7 的实测结论，回写文档 01/03。

## 五、M1 必验清单（把风险烧掉，按优先级）

| 编号 | 要验的事 | 为什么必须现在验 | 判定 |
|---|---|---|---|
| **R-1** 🔴🔴 | **引擎对 Google 翻译的强依赖**（`google-translate-api-x`） | `agent.js` 对**每一条**进入的消息先 `handleEnglishTranslation(message)`，回复前再 `handleTranslation(...)`。**Google 翻译在中国大陆通常不可达** → 整条聊天链路可能在 `try/catch` 里静默失败（引擎只 `console.error` 不重试），**A2 直接不可用**。这是本项目面向中国用户时最可能致命的单点。 | 断网/墙内实测：能聊 → 记录；抛错 → 走**方案 B 之外的第二类补丁**：把 `src/utils/translator.js` 换成直通（我们的提示词本来就是中文，无需英译）或改接国内翻译 API |
| **R-2** 🔴 | `allow_insecure_coding=false` 时敲 `!newAction` 是否真被拒 | `coder.js` **自身没有任何门禁检查**（一手确认），唯一门禁只可能在 `actions.js`；而 `agent.js` 显示**玩家可直接敲该命令绕过 LLM 执行**。这是安全红线的**唯一实际屏障** | 实测被拒 → 记录证据；未被拒 → **必须在 gate 层硬禁该命令名** |
| **R-3** 🔴 | Node 24 是否真的崩 | 决定"应用是否自带 Node 20/22 LTS 运行时"，影响打包体积与架构 | 复现崩溃 → 自带运行时；不崩 → 可省一大块工作 |
| **R-4** 🟡 | 引擎能否被自建 Runner import（方案 A） | 决定"零补丁"还是"单点补丁"，§3.1 | 见 §3.1 判定标准 |
| **R-5** 🟡 | 多 agent 时公屏被屏蔽，我们的接管能否绕过 | 决策 4 允许每服 2 个 bot，这是硬冲突 | 2 个 agent 同时在线，公屏唤醒仍生效 |

## 七、关键取舍备忘（M1 期间不得违背）

1. **模型写的代码绝不在本机执行**（决策 3）。`allow_insecure_coding` 强制 false，且不透传 `INSECURE_CODING`。
2. **密钥与引擎进程权限隔离**（决策 1/3 的推论）。渲染进程与引擎都拿不到明文 key。
3. **成本是一等功能**（决策 5）：非唤醒消息零 token；固定意图零 token；休眠档默认可用。
4. **版本锁 1.21.6**（决策 1b）。
5. **只做中文**（决策 2）。
6. **只有 owner 能指挥**（决策 8），且 gate 必须抢在引擎所有命令执行之前。
7. **进程会被引擎自己杀掉是常态**，不是异常。
8. **不用 Minecraft 原版素材**（版权）。
