## 二、结论先行

1. **用户想要的这个软件，市面上已经有一个中文版雏形：`fandad/Bakabot`。** 它是一个 C#/WPF 的 Windows 桌面启动器，能把 mineflayer 机器人包成图形界面，支持大模型 API 配置、30 多家服务商预设、主人触发模式、人格提示词、多实例管理。**但它只有 2 个 star、只有一个维护者、且核心运行时（"基础包"）不在仓库里**，无法作为可靠依赖。
2. **真正该复用的引擎是 `mindcraft-bots/mindcraft`**（5,842 star / 946 fork / MIT / 持续更新到 2026-10-03）。它是这类应用的**事实标准内核**：mineflayer + 大模型 agent 循环 + `!命令` 动作体系 + 10 个自动模式 + 分层蓝图任务 + 多语言翻译 + 自带 Mindserver。**它已经原生支持 DeepSeek / 通义千问 / ollama。**
   ⚠️ 但它的"记忆"很薄（只有一个地名坐标表 + 每 15 轮压缩到 500 字的摘要，且默认不加载），"建造"只能进程启动时下发任务，这两处都需要我们在应用层补齐。
3. **没有任何一个项目可以直接拿来当我们的应用交付。** 但存在两个极高价值参照物：Bakabot 提供**完整的需求清单**（它把"该有哪些设置项"这件事已经想清楚了），AIMC 提供**目标架构参照**（Electron 包 Mindcraft，但未授权且未完成）。
4. **建议路线：自研桌面壳 + vendor Mindcraft 作为引擎 + 对标 Bakabot 的配置项做我们自己的像素风界面。** 理由：Bakabot 是 WPF（与你要求的像素风、跨技术栈定制都不合），且它的运行时不在仓库内；Mindcraft 是 MIT 可以合法商用再分发。

## 四、重点候选深度分析

### 4.1 Mindcraft —— 引擎首选（MIT，可再分发）

**【一手】核验过的许可证**：MIT License, Copyright (c) 2024 Kolby Nottingham。可自由使用、修改、再分发、商用。

**它是怎么工作的**【一手】：模型不直接操控游戏，而是被要求**输出形如 `!命令名(参数)` 的文本**，由框架解析执行。

```js
const commandRegex = /!(\w+)(?:\(((?:-?\d+(?:\.\d+)?|true|false|"[^"]*")(?:\s*,\s*(?:...))*)\))?/
export function executeCommand(agent, message) { ... }
```
`src/agent/commands/index.js` 把 `queryList`（只读查询）与 `actionsList`（改变世界的动作）拼成命令表，并生成命令文档注入提示词。**这正好印证了文档 01 里"技能是接口，不是提示词"的设计原则** —— Mindcraft 已经是这个架构。

**开箱可用的查询命令**【一手，来自 `src/agent/commands/queries.js`】：
`!stats`（坐标/血量/饥饿/生物群系/天气/当前动作/附近玩家与 bot）、`!inventory`（含装备）、`!nearbyBlocks`、`!craftable`、`!entities`（含村民职业与幼年体 ID）、`!modes`、`!savedPlaces`（记忆库键名）、`!getCraftingPlan(targetItem, quantity)`、`!searchWiki(query)`（实时抓 minecraft.wiki）、`!help`。

**关键发现：Mindcraft 自带"蓝图建造"任务系统——设计正确，但只算半个答案**【一手，详见 `docs/03-Mindcraft引擎能力速查.md` 第二节】：

蓝图结构本身是靠谱的：`{ name, levels: [{ name, placements: [[x,y,z,blockName],...], adjacencies: [...], type? }] }`，**分层推进、逐层校验**（一层完成 = 该层所有 placement 都已存在且 adjacencies 全部满足）。来源有四种：`worldToBlueprint()`（扫描现实世界区域）、`matrixToBlueprint()`、`proceduralGeneration()`、以及任务 JSON。`blueprint.explain()` 能把目标建筑渲染成提示词文本。

**但它有三个硬限制，必须纠正初判**：
1. 🔴 **任务只能"进程启动时"下发，不能聊天下发。`!startTask` 这个命令根本不存在。** 唯一路径是 `main.js --task_path <json> --task_id <id>` → `settings.task` → `new Task(this, settings.task, taskStart)`。
2. **LLM 看不到建造进度**：`!checkBlueprint` / `!getBlueprint` 等 4 个蓝图命令**默认就在 `settings.js` 的 `blocked_actions` 里**。
3. **自由建造只能靠 `!newAction`**，而那是宿主进程内的任意代码执行（见下方红线）。

→ **修正结论**：蓝图机制**消解了"建筑形状从哪来"这个问题**（不用让 LLM 凭空造房子），但**没有解决"玩家在聊天框说'帮我盖个房子'→ bot 就盖"这段链路**。Mindcraft 的模型是**"启动即下发一个建筑任务"**，不是**"聊天中接受建造委托"**。
**这段缺口必须由我们的应用层补上**：聊天里的建造请求 → 转成蓝图/任务 JSON → 带任务参数重启该 bot 进程（或另起一个专职建造的 bot 进程）。**这是一个明确、可估量的自研工作量。**

**`settings.js` 的配置面**【一手，`develop` 分支】—— 这份清单基本就是我们 GUI 要暴露的东西：

**人格配置的形态**【一手，已纠正一次误判】：`andy.json` 极简 —— `{ "name": "andy", "model": "gpt-5.4-mini" }`。
⚠️ **不存在 per-bot 的 `.md` 提示词文件**（`bots/andy/prompts/*.md` 实测 404）。**提示词是 profile 里的 JSON 字符串键**，由 `src/models/prompter.js` **三层合并**：`profiles/defaults/_default.json` → `profiles/defaults/<base_profile>.json`（survival / assistant / creative / god_mode）→ **本 bot 的 profile**，然后创建 `./bots/<name>/` 并写出 `last_profile.json`。
可编辑的提示词键：`conversing`（聊天人格主入口）、`bot_responder`（bot 之间怎么应答）、`coding`、`saving_memory`、`image_analysis`、`speak_model`、`modes`、`conversation_examples`、`coding_examples`、`cooldown`；提示词占位符有 `$NAME` `$STATS` `$INVENTORY` `$ACTION` `$COMMAND_DOCS` `$EXAMPLES` `$MEMORY` `$CONVO` `$SELF_PROMPT` `$LAST_GOALS` `$BLUEPRINTS` 等。
→ **"人格面具编辑器"的可编辑面就是这些 JSON 键 + 三层覆盖关系**，不需要我们去改引擎源码。

**💎 意外收获：10 个现成的"本能开关"**【一手，`src/agent/modes.js`】：`!setMode(mode_name, on)` 命令 + 模式列表，天然就是 GUI 上的一排复选框：

| 模式 | 作用 | 默认 |
|---|---|---|
| `self_preservation` | 逃跑/脱水上岸/离岩浆反射，低血量打断 | ✅ |
| `unstuck` | 无进展则重新寻路/跳跃 | ✅ |
| `cowardice` | 遇敌对生物逃跑而非战斗 | ❌ |
| `self_defense` | 自动攻击敌对生物 | ✅ |
| `hunting` | 猎杀被动动物作食物 | ✅ |
| `item_collecting` | 捡起附近掉落物 | ✅ |
| `torch_placing` | 放火把保持光照 > 0 | ✅ |
| `elbow_room` | 有人靠太近就后退 | ✅ |
| `idle_staring` | 空闲时盯着附近实体看 | ✅ |
| `cheat` | `/setblock` 式捷径（仅 op/创造） | ❌ |

默认值在 `profiles/defaults/_default.json` 的 `"modes"` 键。**这正好落实了文档 01 里 R12（破坏性行为）与 R16（恢复）所需的用户可控性，且零开发成本。**

**🔴 最高等级安全红线：`!newAction(prompt)`**【一手】
它默认被拒（需 `settings.allow_insecure_coding === true`，根 `settings.js` 默认 `false`），但 `main.js` 里有环境变量开关 **`INSECURE_CODING`**。一旦开启则调用 `agent.coder.generateCode()`：**模型写出的 JS 在 agent 进程内直接执行**，作用域里有 `Vec3`、`skills`、`world` 和**活的 mineflayer `bot` 对象**；唯一约束是提示词里"请求"它不要 `import` 库、不要用计时器，而 `code_timeout_mins` 默认 **`-1`（无超时）**。
→ **这等于"任意模型撰写的本地代码执行"**。工程结论：① 我们的应用**默认且强制**保持该开关关闭，并在代码层**拒绝把 `INSECURE_CODING` 透传给子进程**；② **`keys.json` 绝不能与该进程同权限可达**——模型能执行任意 JS 就能读文件；③ 文档 01 中"是否允许模型写代码"应**默认否决**，用我们自己的固定技能表（L3）覆盖需求。

**不可解锁命令**【一手】：`// the unblockable` 列表为 `['!stop', '!stats', '!inventory', '!goal']` —— 即使被配置禁用也依然可用。**我们的"停止"按钮可以直接复用 `!stop` 这一语义。**

**多 bot 机制**：一个 Mindserver 进程托管多个 agent，每个 agent 一套 profile。**但多人格时玩家必须 `/msg` 单独的 bot** —— 这与你"聊天框内出现限定称谓"的需求方向一致但机制不同，需要我们在上层做唤醒路由。

**Mindcraft 已知短板**：
- ✗ 无图形界面（只有浏览器 Web UI），无 Windows 安装包；
- ✗ 官方推荐 **Node 18/20 LTS**，**v24+ 可能与原生依赖冲突**（本机正是 v24.15.0）；
- ✗ 版本支持落后于线上：官方 README 标注支持到 **v1.21.11（推荐 1.21.6）**，而当前线上主流是 **26.1 / 26.2**；
- ✗ 无皮肤、无多服务器列表、无费用统计。

**引擎的集成契约**【一手，`main.js` + `package.json` 实测】—— 这决定了我们的壳**怎么驱动它**：

`main.js` 是唯一入口，用 `yargs` 收两个参数后用**环境变量覆盖配置**，最后直接起 agent：
```js
Mindcraft.init(false, settings.mindserver_port, settings.auto_open_ui);   // 来自 './src/mindcraft/mindcraft.js'
for (let profile of settings.profiles) { settings.profile = JSON.parse(readFileSync(profile,'utf8')); Mindcraft.createAgent(settings); }
```
- 命令行参数：`--profiles <array>`、`--task_path`、`--task_id`（**可执行任务文件里的单个任务**，说明它本身就支持"下发任务"的编程接口）。
- **环境变量覆盖**（对我们极关键）：`MINECRAFT_PORT`、`MINDSERVER_PORT`、`PROFILES`(JSON)、`INSECURE_CODING`、`BLOCKED_ACTIONS`(JSON)、`MAX_MESSAGES`、`NUM_EXAMPLES`、`LOG_ALL`，以及**万能口 `SETTINGS_JSON`**（`Object.assign(settings, JSON.parse(...))`）。
  → **这就是我们的集成方式**：壳为每个 bot 生成一份 profile JSON，然后 `spawn node main.js` 并把 `SETTINGS_JSON` 传进去，**不必改动引擎源码就能完整配置一个 bot**。
- `package.json` 实测：`"type": "module"`，**无 `main`/`exports` 字段 → 它是应用，不是库**；`start` 脚本即 `node main.js`；`postinstall` 跑 **`patch-package`**（所以必须保留 `patches/` 目录，克隆/打包时不能丢）。
- **原生依赖是 Node 版本坑的根源**：`canvas ^3.1.0`、`node-canvas-webgl`、`gl`（在 `overrides` 里被钉到 `^8.1.6`），以及 `three` / `prismarine-viewer` / `minecraft-assets`。这些正是"Node 24 会炸"的元凶。
- 其它关键依赖揭示了能力边界：`ses`（**给 `allow_insecure_coding` 用的安全执行沙箱**——说明它自己也认为这段是危险代码）、`socket.io` + `socket.io-client`（Mindserver 通信）、`express`（Web UI）、`google-translate-api-x`（`language` 翻译）、`cheerio`（`!searchWiki` 抓取）、`minecraft-data`（协议数据）。
- **MIT 是纯 Node 的，没有 Java 依赖**（除可选的 ViaProxy）→ 对 Windows 打包友好。

### 4.2 Bakabot —— 产品形态与需求清单的基准（MIT，但不建议作依赖）

**【一手】核验过的许可证**：MIT License, Copyright (c) 2026 FENTAIIII。**注意版权年是 2026**，且它自述是 `FENTAIIII/ARCbot` 的改版（ARCbot 42 star，原官网 bot.myarc.icu 已关闭）。

**它的架构与关键风险**：启动器（C#/WPF）**本身不含机器人运行时**。用户需自行安装 Node.js 并从一个**交流群里下载"基础包"**，启动器再向该包注入自己的补丁（环境变量桥接、资源包自动接受、聊天触发模式等）后拉起 `node` 子进程。
→ **这条是决定性缺陷**：MIT 只覆盖 C# 启动器，**真正的机器人逻辑不在仓库里、无法审计、无法自托管**。作为开放项目不可依赖。

**但它的"需求清单"价值极高。** 从 `Bakabot/Models/BotInstance.cs` 可见的**按实例配置项**【二手】：

- 服务器：`_mcHost`(默认 `myarc.fun`)、`_mcPort`、`_mcVersion`(默认 `1.20.1`)、`_mcUsername`、`_mcAuthType`(microsoft/offline)、第三方 Yggdrasil 登录 `_authServerUrl`(默认 `https://littleskin.cn/api/yggdrasil`)、`_mcLoginPassword`(AuthMe 自动 `/l`)、`_mcOwnerName`（**"主人"概念**）
- 模型：`_llmApiKey` / `_llmApiUrl` / `_llmModel`，以及**独立的视觉模型** `_visionModel` / `_visionApiUrl` / `_visionApiKey`
- 交互：`_tellMode`(whisper/public)、`_chatTrigger`、**`_triggerMode` 四档 = hybrid / owner_only / keyword_only / owner_keyword**、`_aiStylePrompt`（**人格面具**）
- 本能开关：`_autoDefendEnabled`、`_autoAcceptTpa` + `_tpaOwnerOnly` + `_tpaAcceptTrigger`、`_autoLogin`、`_deathBack`、`_instinctAutoEat/AutoTool/AutoDump`、`_forbidMining`、`_berserkCooldownSeconds`、`_startupGreeting`、`_suppressActionChat`、`_autoAcceptResourcePack`、`_debugMode`
- 其它页面：命令提示词（关键词直达命令，如 `!回` → `/home`）、插件、控制台（日志 + 单实例日志导出并自动脱敏）、QQ（内置 NapCat/OneBot11）、OneBot（6700 端口反向 WS）、设置、外观（暗色模式/拖入图片换背景/强调色）、MCP（`Bakabot.exe --mcp-stdio` 或云端 `/mcp`，让 Claude/Cursor 直接操控机器人）

**从它的更新日志读出的行业实战教训（对我们极有价值）**：

1. **版本兼容是持续成本**：它内置 **ViaProxy 协议代理**才能接 26.2；26.1/26.1.2 靠自带的协议数据直连。这印证了 mineflayer 生态**【一手】至今仍在提 ["Add support for Minecraft Java Edition 26.1.2" · issue #3893](https://github.com/PrismarineJS/mineflayer/issues/3893)**。
2. **反作弊会踢人**：README 明确"机器人加入游戏时可能会触发某些服务器的反作弊系统。如果被踢出，请检查服务器的反作弊设置或调整机器人的行为频率"。
3. **"报成功但东西没了"是合成功能的经典坑**：它记录了两个真实 bug —— `CraftItem` 自己开一次工作台、mineflayer 内部又开一次，导致"合成在客户端成功、却被服务器回滚"；以及 `has_items` / `items` 字段名不一致导致前置条件检查**从未生效**。
4. **任务连贯性的正确做法**：每个步骤不能自己宣布成功，必须有**产物验真**（合成后确认物品真进背包、丢弃后确认背包数量真减少）+ 步骤间前置条件校验。
5. **多账号登录的实现细节**：通过 ViaProxy 进正版服时，机器人以离线身份连本地代理，真正的正版验证由代理用所选微软账号完成；实例里填的机器人用户名**不参与正版验证**。
6. **第三方皮肤站登录**：`littleskin.cn`（LittleSkin）的 Yggdrasil API 是中文离线服圈的主流方案 —— **这可能才是你"bot 皮肤"需求真正该走的路径**。
7. **一个真实的工程事故教训**（写在仓库开头）：**禁止按进程镜像名杀 `java`/`node`** —— 用户的 Minecraft 客户端进程名就是 `java.exe`，按名字杀会静默杀掉玩家正在玩的游戏（无日志、退出码 -1）。任何"重启/清理/构建前先杀进程"都必须按命令行特征或精确 PID。
8. 它承认代码由生成式 AI 参与编写，由维护者审阅担责 —— 这也解释了它 2 star 却功能齐全。

**为什么最终不选它**：① WPF/C# 无法满足你要的像素风自绘与跨栈定制；② 运行时不在仓库内；③ 2 star / 单人维护 / 无社区验证；④ 无皮肤 UI、无建造蓝图。

### 4.3 AIMC —— 架构最接近，但**不能碰**

`zhongli369/AIMC` 自述"基于 Mindcraft 重构，集成 Zod 校验、安全护盾、语音管道和 Electron 桌面启动器"，流程为
`DeepSeek → AgentOutput JSON → Zod 校验 → SafetyGuard → ActionDispatcher → Mineflayer`，
目录含 `electron/`、`src/runtime`(Zod+SafetyGuard+dispatcher)、`src/agent`(AgentCore think loop)、`src/llm`、`src/voice`(Whisper.cpp + Edge-TTS)、`src/memory`(SQLite + 混合检索)、`src/personality`(同伴/建造者/探索者/守卫 4 预设)、`src/legacy`(整个 Mindcraft)。

**这几乎就是文档 01 里我们画的架构的现成实现**，尤其是**"Zod 校验 + SafetyGuard 插在模型输出与动作分发之间"**这一条，正是应对风险 R13（提示注入）与 R14（模型乱输出）的正确工程手段。

**但**：仓库**无 LICENSE 文件**（`license` 字段为 null）→ 法律上不可复用任何代码；1 star；2026-05-27 后停更；README 自述语音/记忆/人格模块**尚未接入 Electron UI**。
→ **只作为架构思路参考，一行代码都不要抄。** 我们自己在 Mindcraft 之上实现同样的"校验层 + 安全盾"。

### 4.4 其余项目：不值得作为依赖，但值得读

- **Multi-Bot**：无 LLM，纯 `Bot.*` 脚本命令。可读它的**分组 + 目标选择 + Socket.IO 实时状态推送**这类 UI 模式。
- **aibot_minecraft**：Electron + Ollama，单 bot、俄文、2026-01 起停更。可读它的**手动 WASD 控制台、拖拽式背包、Memory Matrix 记忆编辑**这些界面点子。
- **VillagerAgent**：ACL 2024 论文项目，99 star，但锁死 MC **1.19.2**、纯 CLI、需 `/op`。只用于**多智能体协作**的思路参考。

### 4.5 学术与研究级项目：**全部不可用**，但 Voyager 的设计必须学

调研代理普查了研究界阵营，结论是**没有一个能作为产品基座**，原因归为四类：

| 项目 | 许可证 | ★ / 状态 | 锁定版本 | 不可用的原因 |
|---|---|---|---|---|
| **Voyager** (MineDojo) | MIT | 7,245 / **2024-04-03 后停更（约 2.5 年）** | **Java 1.19 + Fabric**（fabric-loader-0.14.18-1.19） | 需 OpenAI GPT-4、仅限 LAN、无人维护；自带的是**fork 出来的旧 Mineflayer** |
| MineDojo | MIT≈ | ≈2,200 / ~2023 已死 | **1.16.5 模拟器** | 基准/模拟器，非运行时；[Windows 安装已损坏 (issue #39)](https://github.com/MineDojo/MineDojo/issues/39) |
| MineRL | NOASSERTION | 977 / 2025-01-22 | **1.16.5**，JDK 8 | 无头模拟器 |
| VPT (OpenAI) | MIT≈ | ≈1,200 / 2023 冻结 | MineRL 1.16.5 世代 | 基座模型，无联服路径；需 GPU |
| STEVE-1 | MIT≈ | 2023–24 | MineRL 1.16.5 世代 | 研究代码，依赖 MineRL |
| JARVIS-1 | 无 | ≈1,000 / ~2024 停滞 | MCP-Reborn 旧客户端 | **仅 Linux**、发布不完整（`learning.py` 为 TODO） |
| Optimus-1 / -2 | research | NeurIPS24 / CVPR25 | 模拟器 | VLM/VLA 训练代码，非 agent 运行时 |
| Odyssey | MIT(码)/CC BY-NC-SA(数据) | IJCAI 2025, 活跃 | 真服务器 | 需本地 GPU 跑 LLaMA3 8B/70B + 全栈 |
| Cradle | MIT | ~2024 | — | **已把 Minecraft 从环境列表移除**，转向 RDR2/Stardew/桌面 |
| Project Sid (Altera) | 无 | 2024 | — | **只有报告、没有代码** |

**关键教训：研究界的项目都绑死在"模拟器 + 特定旧版本 + GPU + Linux"上，与"Windows 桌面应用 + 真实多人服务器"是完全不同的物种。** 但它们验证了两件事：Voyager 的**技能库（skill library）+ 迭代式提示**是本项目要复刻的核心设计（文档 01 的 L3 技能层正是这个），Mineflayer 是研究界与工业界共同的底层事实标准。

> **反面清单**：`Mineflayer 无法驱动 MineRL 模拟器`，研究栈的 1.19(Fabric) 与 1.16.5(MineRL/MineDojo) 是两个不兼容的世代 —— **不要把研究栈和产品栈混用**。

### 4.6 低层积木层 —— 真正可以放心依赖的那一层

上层项目都在剧烈变动，但这一层是**稳定、活跃、MIT、零 GPU、纯 Node** 的，本项目的可靠性最终建立在这里。

- **[PrismarineJS/mineflayer](https://github.com/PrismarineJS/mineflayer)** — MIT，**7,539★，2026-10-03 仍在推送**。**支持 MC 1.8 → 26.1**（含 1.19 / 1.20 / 1.21 / 1.21.9 / 1.21.11 / 26.1），要求 **Node ≥18**，**能自动探测服务器版本**，`auth: 'offline' | 'microsoft'`，支持 Realms。文档在仓库的 `docs/README.md`。
  → **这一条极大缓解了版本焦虑**：真正跟得上线上版本的其实是 mineflayer 本身（已到 26.1），落后的只是 Mindcraft 打包的那一套（锁到 1.21.11）。
- **[mineflayer-pathfinder](https://github.com/PrismarineJS/mineflayer-pathfinder)** — MIT，A* 寻路，Baritone 风格的 Goal 集合（`GoalBlock` / `GoalNear` / `GoalXZ` / `GoalFollow` / `GoalComposite` / `GoalPlaceBlock` / `GoalLookAtBlock`），可配置挖掘/放置/跳跃/搭 1×1 塔的代价与禁区。
  → **💎 本次调研最有价值的单项发现：`createHuman(bot, { seed })`**。它给出**纯追踪式行走**（绝不会像机器人那样死板地对齐到方块中心）、按真实 0.15° 鼠标网格转头、人类化的疾跑与疾跑跳时机，并且**用一个 seed 派生每个 bot 各不相同的"性格"参数**：`basePitch`、`turnTime`、`sprints`、`jumpRate`、`lookAhead`、`stopRadius`、`reaction`、`glances`、`strafe`、`deadband`。还带服务器传送（setback）保护。
  → **一举解决三个需求**：① 反作弊风险 R10（行为像人）；② 多 bot 同服时的个体差异（每人一个 seed）；③ 陪伴感的"活人味"。这必须是 M1 就要接上的东西。
- **[mineflayer-collectblock](https://github.com/PrismarineJS/mineflayer-collectblock)** — MIT。`bot.collectBlock.collect(block)` 一条调用 = 寻路 + 自动换工具 + 挖掘 + 捡掉落 + 背包满时存箱子。**"帮忙搜集原材料"这个需求基本就是它。**
- 其它零 GPU 插件：**mineflayer-pvp**（战斗）、**mineflayer-tool**（自动换合适工具）、**MineflayerArmorManager**、**mineflayer-statemachine**（状态机）、**prismarine-viewer**（无头渲染截图——当前研究界做"实时画面"的标准栈，如 arXiv:2505.20148）、**PrismarineJS/mineflayer-builder**（在生存模式下按 schematic 建造，且保持朝向）。
- **[cabaletta/baritone](https://github.com/cabaletta/baritone)** — **LGPL-3.0**，Java，**9,256★，2026-09-29 仍在推送，当前分支 1.21.4**。最强寻路/挖掘/建造，并且**支持按 Litematica schematic 施工**（`LitematicaCommand.java` 实现了 `#litematica` 指令）。
  → **这是"大规模按图纸建造"唯一现实的路线**。但代价明确：它是**客户端 Fabric mod，不是可嵌入的库** —— 意味着要为每个 MC 版本随包附带一个真实 Java 客户端 + Fabric loader，对桌面应用是重负担。**建议作为二期可选高级功能**，不要进 M1。
- **MCP 路线**：**[HarjjotSinghh/minecraft-mcp](https://github.com/HarjjotSinghh/minecraft-mcp)** → npm 包 **`minecraft-ai-mcp`**（MIT，`npx -y minecraft-ai-mcp`，约 30 个工具：goto/follow/dig/place/craft/attack/send_chat/get_inventory/collect_block…，支持 offline + Microsoft 验证，MC **1.8–1.21+**，有 Claude Desktop / Cursor 配置，无头）。
  → 对"用工具调用型大模型控 bot"是最快路径，但**一次只能一个 bot**，且多一层 IPC。**判定：可作为"高级用户直连 Claude/Cursor"的附加能力（与 Bakabot 的 MCP 页面同思路），不作主运行时。**

### 4.7 顺带发现的 Mindcraft 关键优势：原生中文模型支持

调研确认 Mindcraft 的 provider 列表**已包含 DeepSeek、Qwen（国际版 + 国内版）、ollama、OpenAI、Anthropic、Google**，TTS 支持 OpenAI/Google。
→ 这直接满足了"接入任意大模型 API"里最实用的那部分（**DeepSeek / 通义千问做中文陪伴对话**），**不需要我们自己写适配器**。同时也印证了文档 01 的 D1 决策方向正确：以 **OpenAI 兼容端点**为通用适配层，DeepSeek/Qwen/Ollama 都天然落在里面。

## 五、三个硬约束（调研后确认，必须写进设计）

### 5.1 版本兼容 —— 风险比预想小，但必须显式管理

需要区分**两层**，这是本次调研最重要的认知修正：

| 层 | 支持的 MC 版本 | 事实 |
|---|---|---|
| **mineflayer（底层协议）** | **1.8 → 26.1**，自动探测 | 7,539★，2026-10-03 活跃。**它跟得上线上版本。** |
| **Mindcraft（打包好的引擎）** | **≤ 1.21.11**（推荐 1.21.6） | 落后于 mineflayer，因为它固定了一套自己的依赖版本 |

- mineflayer **尚不支持 26.1.2 / 26.2**（仍有 open issue：[PrismarineJS/mineflayer#3893 "Add support for Minecraft Java Edition 26.1.2"](https://github.com/PrismarineJS/mineflayer/issues/3893)）——也就是说**"26.1 能连、26.1.2 与 26.2 连不了"**。
- Mindcraft 能接 26.2，靠的是 **ViaProxy 协议代理**（需 Java 17+，多一层进程与故障点）。
- 三条应对路径（按优先级）：
  1. **产品把"目标服务器版本"做成一等公民配置项**，接服前先探测服务器版本，并给出"可直连 / 需协议代理 / 暂不支持"的明确判断与引导；
  2. 在 **Mindcraft 之上把 mineflayer 与 minecraft-data 升到当前版本**，自测后可吃掉 1.21.11 → 26.1 这段差距（这属于 fork 后的第一批改造）；
  3. **按需可选启用 ViaProxy**，兜住 26.2 及以后。
- **结论**：不把版本当成"以后再说"的风险，而是当成 UI 上的一等状态（绿色可直连 / 黄色需代理 / 红色不支持）。

### 5.2 皮肤 —— 没有现成界面，但引擎里有一个可改写的挂点

- **【修正】没有任何候选项目提供面向用户的皮肤设置界面；但 Mindcraft 引擎源码内已有皮肤挂点。** 一手读 `src/agent/agent.js` 的 `login` 事件：
  ```js
  // Set skin for profile, requires Fabric Tailor. (https://modrinth.com/mod/fabrictailor)
  if (this.prompter.profile.skin)
      this.bot.chat(`/skin set URL ${this.prompter.profile.skin.model} ${this.prompter.profile.skin.path}`);
  else
      this.bot.chat(`/skin clear`);
  ```
  即 **profile 里写 `skin: { model, path }`** 就会在每次登录时执行这条命令。注释指明目标 mod 是 **Fabric Tailor**。⚠️ 但我们的 bot 是 **mineflayer 无头客户端，装不了客户端 mod**，所以这条命令**只有在服务端存在能识别该语法的插件时才有意义**（SkinsRestorer 是另一套语法）。因为我们 vendor 了源码，**这个挂点可以直接改成我们需要的形式**——比从零实现便宜得多。详见 `docs/03-Mindcraft引擎能力速查.md` §9.5。
- 社区里这仍是一个长期痛点：**【一手】mineflayer 的 [issue #2269 "SkinRestorer plugin: Some mineflayer features don't work if you change the skin"](https://github.com/PrismarineJS/mineflayer/issues/2269)** 与 [discussion #1800 "How do you add skins to Mineflayer Bot?"](https://github.com/PrismarineJS/mineflayer/discussions/1800) 说明：**改皮肤会影响 bot 的部分功能**，且有实现门槛。
- 现实可行的路径（按场景）：
  1. **离线服 + LittleSkin 等皮肤站 Yggdrasil 登录**（Bakabot 已验证可行）——皮肤随账号走，最完整；
  2. **服务器装了 SkinsRestorer** 等皮肤插件 → 通过指令换肤，但有副作用（见 issue #2269）；
  3. **服务端资源包/自定义模型** → 可改变外观但需客户端配合，超出 bot 控制范围；
  4. **正版服** → 只能使用该微软账号自带的皮肤。
- **结论**：GUI 上的"皮肤"必须**按服务器场景显示可用选项并标注生效条件**，不能做成一个无条件生效的下拉框。

### 5.3 运行时与 Node 版本

- Mindcraft 官方推荐 **Node 18/20 LTS**，明示 **v24+ 可能有原生依赖问题**；本机是 **v24.15.0**。
- **结论**：应用**自带 Node 20/22 LTS 运行时**（随包分发），既避开版本坑，又满足"用户零环境依赖"的易用性要求。

## 六、选型建议

### 6.1 推荐方案：自研壳 + vendor Mindcraft

| 层 | 选型 | 理由 |
|---|---|---|
| 桌面壳 | **自研（Electron 或自研 WebView 壳）** | 需要像素风完全自绘 + 多服务器并行面板；WPF 无法复用、纯 Web 又缺系统集成 |
| Bot 引擎 | **vendor `mindcraft-bots/mindcraft`（MIT）** | 唯一成熟、活跃、可合法再分发的 LLM×MC agent 内核；命令动作体系与我们的"技能层"设计完全同构；**且已原生支持 DeepSeek / Qwen** |
| 拟人化与差异化 | **`mineflayer-pathfinder` 的 `createHuman(bot,{seed})`** | 每 bot 一个 seed → 走路/转头/疾跑/跳跃都像人且各有个性，同时压低反作弊风险 |
| 采集与建造执行 | `mineflayer-collectblock` + Mindcraft 蓝图任务（+ 二期可选 Baritone `#litematica`） | 采集有现成一条调用；蓝图分层结构正确；超大型建筑留给二期 |
| 版本探测 | **`mineflayer` 自带的版本自动探测** + 版本状态 UI | 引擎本身就支持 1.8→26.1，不需要我们自己造 |
| 引擎加固 | 参考 AIMC 的思路**自研 `Zod 校验 + SafetyGuard + ActionDispatcher` 中间层** | 应对提示注入与模型乱输出；**不抄代码，只借思路** |
| 协议兼容（兜底） | 内置 **ViaProxy** 作为可选组件 | 唯一的跨版本现实解法（26.2 及以后） |
| 配置面 | **以 Bakabot 的 `BotInstance.cs` 字段集为验收清单** | 它已经把这类产品该有的设置项踩过一遍坑 |
| 皮肤 | LittleSkin/Yggdrasil 登录 + SkinsRestorer 指令（按场景降级） | 无现成界面；**引擎内有一个可改写的挂点**（`profile.skin`），仍需自研与适配 |
| 人格面具 | Mindcraft profiles + 我们的提示词编辑器 | 已有 profile 机制可挂靠 |
| 建造 | **Mindcraft 蓝图任务（仅"启动时下发任务"）+ 我们必须自研的"聊天委托 → 生成任务 → 重启进程"链路**（二期可选 Baritone `#litematica` 做大工程） | 蓝图结构现成且分层正确，但 `!startTask` 不存在、`!checkBlueprint` 默认被屏蔽——**聊天中接建造委托这一段是我们的活** |

### 6.2 为什么不直接用 Bakabot

- 它确实是最接近的产品，**但它是 C#/WPF、运行时不在仓库、2 star 单人维护**。用它的唯一合理方式是"运行它作为临时验证工具"，而不是作为我们的代码基。
- **它的正确用法是：当成一本写好的需求规格书和避坑指南。**

### 6.3 为什么不从零写一切

- 用户明确要求复用开源；且 Mindcraft 已积累 5.8K star 的迭代，包含命令体系、蓝图任务、模式系统、记忆库、TTS、多语言翻译等，从零复刻是数月级浪费。

## 九、本步结论与下一步

1. 调研目标达成：**找到了可复用的引擎（Mindcraft, MIT, 5.8K star）**，也**找到了需求形态的完整参照（Bakabot）**，两条线都验证了文档 01 的架构判断；并额外产出了一份引擎对照表 `docs/03-Mindcraft引擎能力速查.md`。
2. 调研**修正了五点认知**（每一条都改变了工作量估计）：
   1. **版本兼容没那么绝望**——真正跟得上线上的是 mineflayer（1.8→26.1，自动探测版本），落后的是 Mindcraft 打包的那一套（≤1.21.11）。差距可以通过升级依赖 + 可选 ViaProxy 兜底来管理。
   2. **建造只有半个答案**——蓝图结构现成且分层正确，但 `!startTask` 不存在、任务只能进程启动时下发、`!checkBlueprint` 默认被屏蔽。**"聊天里接建造委托 → 生成任务 → 重启进程"这段链路是我们必须自研的**。
   3. **人格提示词不是 `.md` 文件而是 profile 里的 JSON 键**（三层合并），人格面具编辑器因此可以完全不动引擎源码。
   4. **有 10 个现成的"本能开关"**（`!setMode` + `modes.js`），零成本落实用户可控性。
   5. **`!newAction` 是宿主进程内的任意代码执行**（默认关，但 `INSECURE_CODING` 环境变量可一键打开，且默认无超时）→ 这条红线决定了我们的密钥必须做运行时隔离，也决定了"是否允许模型写代码"应默认否决。
3. 另外确认了两条硬约束：**皮肤在所有现成方案的 GUI 里都是空白且改皮肤有功能性副作用**（mineflayer issue #2269；但引擎内有 `profile.skin` 挂点可改写，见 §5.2）；**Node 24 会炸**（`canvas` / `node-canvas-webgl` / `gl` 原生依赖，且 `spawn` 时无条件调用 `addBrowserViewer`），必须自带 Node 20/22 LTS 运行时。
4. **所有候选项目都缺失同一块拼图：像素风 GUI + 多服务器并行 + 皮肤。** 这正是本项目的差异化所在，也正是必须自研的部分。
5. **当初的唯一阻塞项已解除**：文档 01 第八节的 9 项决策已由用户于 `m00220` / `m00224` 全部确认（离线自建服、MC 1.21.6、首期中文、否决模型写代码、1–2 服 × 1–2 bot、成本优先、皮肤场景化降级、不做 3D 预览、仅房主可指挥）。现已可进入 M1 走通最小闭环，实施计划见 `docs/04-M1实施计划.md`。
